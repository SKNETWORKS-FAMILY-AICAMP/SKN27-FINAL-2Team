# 취약점 분석 개선 — 협조 요청서

`docs/study_plan/취약점_분석_개선_설계.md`의 개선 작업은 `app/analytics` 내부와
마이페이지·오답률 상세 프론트까지를 직접 수정 범위로 한다.
범위 밖 두 건을 아래와 같이 담당자 반영을 요청한다. 반영 전까지 해당 화면은
기존 기준·표현으로 동작하며, 이 기간의 불일치는 알려진 한시적 상태다.

---

## 요청 1. 오답노트 취약 조합 로직 교체 (question 앱)

### 배경

`app/question/views.py`의 `_wrong_note_top_combinations()`는 오답노트 문제 생성용
취약 조합(era+topic+q_type)을 자체 로직으로 뽑는다: 완료 기록을 조합별로 묶어
**오답 1건 이상이면 포함**하고 raw 오답 수·오답률로 정렬한다.

analytics 개선 후에도 이 로직이 그대로면, 마이페이지·오답률 상세·학습계획은 새 기준
(표본 보정 + 최근성 감쇠)으로 "취약"을 판정하는데 오답노트만 옛 기준으로 조합을 골라
**사용자가 화면마다 다른 취약점을 보게 된다.** 예: 마이페이지에서 사라진
"1문항 중 1오답" 조합이 오답노트 추천에는 계속 등장.

### 요청 내용

1. `_wrong_note_top_combinations()`의 조합 선정을 analytics가 제공하는 공용 판정으로 교체:

```python
from analytics.service.weakness import build_weakness_rows

rows = build_weakness_rows(record_qs, group_fields=["era", "topic", "q_type"])
# today 인자는 기본값(None → timezone.localdate())이 있어 생략 가능. 테스트에서만 주입한다.
```

2. 포함 조건을 "오답 1건 이상" → **`status in (WEAK, NEUTRAL)`** 로 교체.
   (INSUFFICIENT = 표본 부족, STABLE = 안정 조합은 제외된다. 임계값·보정은 함수 내부에서
   처리되므로 호출부는 row의 `status` 값만 보면 된다.)
3. 정렬을 raw 오답 수 기준에서 `row["weaknessScore"]` 내림차순으로 교체.
   동률 시 `row["raw"]["wrong"]` 내림차순 → `row["groupKeyId"]` 오름차순으로 안정 정렬한다.

   **반환 스키마와 변환**: build_weakness_rows의 행 스키마는 설계 문서 5장이 기준이다.
   기존 오답노트 조합 dict로의 변환은 다음 매핑으로 한다 — era/topic은
   `row["group"]["era"]`, `row["group"]["topic"]`에서 가져오고, q_type은 설계 문서 스키마의
   camelCase 키인 `row["group"]["qType"]`에서 가져와 기존 응답의 `q_type` 필드로 변환한다.
   정오 집계는 `row["raw"]`(total/wrong)에서 가져오고, 조합 식별이 필요하면
   `row["groupKeyId"]`(canonical string)를 그대로 키로 쓴다
   (문자열이므로 dict 키·비교에 바로 사용 가능).
   기존 API 응답 형태는 유지해야 한다: `rank`, `era`, `topic`, `q_type`, `wrong_count`,
   `total_count`, `wrong_rate`, `question_count` 필드를 그대로 반환한다. `wrong_rate`는 현행처럼
   퍼센트 단위 숫자(예: 37.5)로 변환하고, `question_count`는 기존 `_allocate_wrong_note_counts()`와
   `WRONG_NOTE_TOP_LIMIT` 배분 규칙을 유지한다.
4. 후보가 부족할 때(신규 사용자)의 폴백은 **오답노트 전용 폴백**으로 적용한다:
   ① `status == INSUFFICIENT`라도 오답이 있는 조합(`row["raw"]["wrong"] > 0`) 포함
   → ② 기존 방식(raw 오답 수 정렬) 유지.
   (기본 조건이 이미 NEUTRAL을 포함하므로 "NEUTRAL 포함" 단계는 없다.
   설계 문서 6장(학습계획)의 마지막 폴백은 "출제 예상만으로 구성"이지만, 오답노트는
   사용자의 오답에서 출제하는 기능이라 출제 예상 폴백이 취지에 맞지 않아 ②를 기존 방식으로 둔다.)

### 제공 사항 (analytics 측)

- `build_weakness_rows()` 함수와 산출 스키마 (설계 문서 5장): 조합별 raw/보정 점수/status/trend
- 골든 케이스 단위 테스트 (설계 문서 9.1) — 호출부 검증에 재사용 가능

## 요청 2. 결과 화면 "취약" 계열 문구 조정 (diagnosis / study / question 템플릿)

### 배경

다음 결과 화면 3곳이 방금 풀이한 세션/문항의 raw 오답 기록 기반으로 "취약 TOP 3"류 표현을 쓴다.
`diagnosis/result.html`과 `study/result.html`은 raw `wrong_rate` 정렬을 쓰고,
`question/question_result.html`은 틀린 문항의 유형 목록을 직접 뽑는다.

- `templates/diagnosis/result.html` (116행 부근)
- `templates/study/result.html` (124행 부근)
- `templates/question/question_result.html` (115행 부근)

이번 개선으로 "취약"은 표본 보정·최근성이 반영된 판정 용어가 된다. 결과 화면은
"방금 그 세션의 기록"이라 raw 표시가 맞지만, 같은 단어 "취약"을 raw 기준으로 쓰면
마이페이지의 취약 판정과 사용자가 혼동한다.

### 요청 내용

수치·정렬 로직은 그대로 두고 **문구만 조정**한다. 대상은 "취약 TOP 3"뿐 아니라
"취약 유형", "취약 시대" 등 화면 내 "취약" 계열 표현 전체다:
"취약 TOP 3" → "오답 TOP 3", "취약 유형" → "오답 많은 유형" 류.
서버 로직 변경 없음, 템플릿 문구 수정만.

## 일정 의존성

```text
analytics 1~2단계 (판정 모듈 + 캘리브레이션) 완료
  → analytics 3~5단계 + 마이페이지/오답률 상세 프론트 반영   ← 이 시점부터 미반영 화면과 불일치
  → 요청 1 (오답노트 로직)                                  ← 기준 불일치 해소
  → 요청 2 (결과 화면 라벨)                                 ← 용어 혼동 해소 (요청 1과 순서 무관, 독립 반영 가능)
```
