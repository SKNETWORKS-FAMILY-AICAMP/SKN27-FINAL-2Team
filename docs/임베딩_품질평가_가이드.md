# 임베딩 품질평가 가이드

## 1. 목적

임베딩 품질평가는 사용자의 역사 개념 질문에 대해 RAG가 관련 chunk를 상위 결과로 잘 찾아오는지 확인하는 과정이다.

평가 대상은 PostgreSQL의 `rag.document_chunks` 테이블에 저장된 `embedding`, `chunk_text`, `metadata`이다.

## 2. 평가 기준

초기 단계에서는 정답 생성 품질보다 검색 품질을 먼저 본다.

핵심 지표:

```text
- Recall@K: 정답 근거가 상위 K개 안에 들어왔는가
- MRR: 첫 번째 정답 근거가 몇 번째에 나왔는가
- nDCG@K: 더 좋은 근거가 더 위에 배치됐는가
- Metadata Hit: 시대, 분야, 개념 태그가 필터에 잘 걸렸는가
- Source Mix: 신편 한국사, 사료, 이미지 자료가 질문 성격에 맞게 섞였는가
```

초기 추천 기준:

```text
Recall@5 >= 0.8
MRR >= 0.6
이미지 질문의 image_material 포함률 >= 0.7
개념 질문의 historical_overview 포함률 >= 0.7
```

## 3. 골든 질문 세트 만들기

먼저 사람이 직접 평가 질문과 기대 근거를 만든다.

예시:

| query | expected_keywords | expected_era | expected_source_type |
|---|---|---|---|
| 조선 전기 6조 직계제 설명해줘 | 6조, 직계제, 태종, 의정부 | 조선 전기 | historical_overview |
| 전시과가 뭐야 | 전시과, 고려, 토지 제도 | 고려 시대 | historical_overview |
| 연천 전곡리 유적 사진 보여줘 | 연천, 전곡리, 주먹도끼 | 선사 | image_material |
| 권문세족과 신진 사대부 차이 알려줘 | 권문세족, 신진 사대부, 고려 말 | 고려 시대 | historical_overview |
| 훈민정음 창제 배경 정리해줘 | 훈민정음, 세종, 집현전 | 조선 전기 | historical_overview |

처음에는 30개 정도로 시작하고, 기능이 안정되면 100개 이상으로 늘린다.

## 4. SQL로 직접 확인하는 방법

특정 질문의 임베딩 벡터를 만든 뒤 pgvector cosine distance로 검색한다.

```sql
SELECT
  chunk_id,
  source_type,
  title,
  metadata->>'source_url' AS source_url,
  metadata->>'thumbnail_url' AS thumbnail_url,
  metadata->>'original_image_url' AS original_image_url,
  1 - (embedding <=> '[질문_임베딩]'::vector) AS vector_score,
  left(chunk_text, 200) AS snippet
FROM rag.document_chunks
WHERE embedding IS NOT NULL
ORDER BY embedding <=> '[질문_임베딩]'::vector
LIMIT 5;
```

실제 서비스에서는 SQL에 직접 벡터 문자열을 넣기보다 Python에서 파라미터 바인딩으로 전달한다.

## 5. 사람이 보는 체크리스트

상위 5개 결과를 보고 아래를 체크한다.

```text
1. 질문의 시대가 맞는가
2. 질문의 핵심 개념이 제목이나 본문에 들어 있는가
3. 설명에 바로 쓸 수 있는 chunk인가
4. 너무 넓거나 엉뚱한 배경 자료가 상위에 오지 않는가
5. 이미지 요청일 때 이미지 URL이 있는 자료가 포함되는가
```

평가 예시:

```text
query: 조선 전기 정치 정리해줘
top1: 조선 초기의 정치구조
판정: 적합

query: 연천 전곡리 유적 사진 보여줘
top1: 연천 전곡리 유적 전경
판정: 적합, original_image_url 있음
```

## 6. Hybrid RAG 품질평가

최종 챗봇은 벡터 검색만 쓰지 않고 아래 점수를 합친다.

```text
hybrid_score =
  vector_score * 0.55
  + keyword_score * 0.30
  + metadata_score * 0.15
```

질문 유형별로 가중치를 다르게 줄 수 있다.

```text
개념 설명 질문:
  historical_overview 가중치 증가

사료 근거 질문:
  historical_source 가중치 증가

이미지/사진 질문:
  image_material 가중치 증가
  original_image_url 또는 thumbnail_url 존재 여부 가산
```

## 7. 개선 판단 기준

검색 결과가 안 좋을 때는 원인을 나눠서 본다.

```text
1. chunk가 너무 큰가
   - 핵심 개념이 긴 본문에 묻히면 chunk_size를 줄인다.

2. 질문 표현과 본문 표현이 다른가
   - 동의어 사전을 추가한다.
   - 예: 6조 직계제, 육조 직계제, 직계아문

3. 시대 필터가 약한가
   - metadata.chronology.era, era_order를 검색 조건에 반영한다.

4. 이미지 자료가 안 뜨는가
   - source_type=image_material 가중치를 올린다.
   - original_image_url 존재 여부를 가산한다.

5. 특정 자료만 과도하게 뜨는가
   - source_type별 가중치를 조정한다.
```

## 8. 현재 프로젝트 권장 순서

```text
1. 골든 질문 30개 작성
2. PostgreSQL vector 검색 top5 결과 확인
3. keyword + metadata 점수 추가
4. Recall@5, MRR 수동 계산
5. 실패 질문만 따로 모아 chunking, metadata, 동의어 개선
6. 답변 생성 품질은 검색 품질이 안정된 뒤 평가
```
