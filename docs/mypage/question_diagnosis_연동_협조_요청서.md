# 학습계획 연동 최소 협조 요청서 — question·diagnosis

상태: DRAFT (협의 전)  
작성일: 2026-07-20  
요청 부서: analytics  
요청 대상: question·diagnosis 담당  
관련 문서: [학습계획·AI 주간리포트 통합설계](./학습계획_AI주간리포트_통합설계.md)

## 1. 요청 목적

기존 question·diagnosis 연동을 최대한 유지하면서 analytics만으로 막을 수 없는 동시 시작, 데이터 삭제 위험, diagnosis 일부·동시 제출, 계획 블록의 잘못된 새 시작, 보관 계획 완료 전달 누락, 앱별 학습일 불일치를 보완하려 한다.

계획 JSON 조회, 블록 완료, 주간평가 세션 확인, 리포트 대기 등록, 중복 방지와 복구는 analytics에서 기존 인터페이스와 풀이 기록을 이용해 처리한다.

## 2. 현재 동작 중이므로 변경 요청하지 않는 항목

### question

- 진행 중 일반 문제풀이 최대 1개 정책
- 기존 세션 삭제와 새 세션·문항 생성을 묶은 트랜잭션
- 진행 중 목록 GET의 읽기 전용 처리
- 계획 번호(`studyplan_id`)·블록 번호(`study_plan_block_id`) 저장
- 풀이 기록에 사용자 선택 답과 정답 저장
- 전체 답안 제출 트랜잭션과 analytics 블록 완료 함수 호출

현재 시작·제출 API 구조와 analytics 완료 함수 호출 형식은 유지한다. 시작·제출 API 변경은 시작 동시성 잠금, 계획 블록 새 시작의 예정일·종료 상태 검증, 보관 계획에 연결된 기존 세션의 완료 전달로 제한한다.

### diagnosis

- 평가 구분(`solve_sessions.review_type`)
- 일반 진단평가와 주간평가의 삭제 범위 분리
- 계획 번호·블록 번호 저장
- 제출 후 analytics 블록 완료 함수 호출

평가 구분 필드 추가나 제출 함수 호출 형식 변경은 요청하지 않는다. 제출 내부에는 세션 잠금·전체 문항 검증·트랜잭션 보강만 요청한다.

## 3. question 필수 요청 — 시작 잠금·블록 검증·보관 계획 완료

대상: `app/question/views.py`에서 기존 진행 세션을 삭제하고 새 세션을 만드는 모든 일반 문제풀이 시작 경로

현재 삭제와 생성은 트랜잭션으로 묶여 있지만 동일 사용자의 두 시작 요청이 동시에 들어오면 각각 새 세션을 만들 수 있다.

요청 사항:

- 기존 시작 트랜잭션 진입 직후 사용자 행을 `SELECT ... FOR UPDATE`로 잠금
- 사용자 잠금 뒤 기존 진행 세션을 다시 조회하고 삭제
- 같은 트랜잭션에서 새 세션과 전체 풀이 기록 생성
- 같은 사용자의 모든 일반 문제풀이 시작 경로에서 사용자 → 세션 순서로 잠금
- 계획 블록으로 새 세션을 시작할 때 analytics 호환 창구의 계획 블록 시작 검증 함수(`validate_study_plan_block_start`)를 호출해 활성 계획 소유권과 문제풀이 실행 경로를 확인
- 같은 검증 결과로 블록 예정일이 `Asia/Seoul` 기준 오늘이고 풀이 기록을 반영한 블록 상태가 예정 또는 진행 중인지 확인하며, 미래·과거 날짜는 `409 BLOCK_NOT_DUE`, 완료·놓침·취소 상태는 `409 BLOCK_TERMINAL`로 차단
- 기존 진행 세션 이어풀기는 새 시작 검증과 분리하고 원본 계획이 보관 상태여도 기존 세션·문제·임시 답안을 반환
- 기존 세션 제출 완료 시 풀이 기록에 연결된 원본 계획이 활성 또는 보관 상태이면 기존 analytics 블록 완료 함수를 호출하고, question 내부의 활성 계획 전용 사전 조회 때문에 호출을 생략하지 않음
- 제출·이어풀기·진행 중 목록 응답 형식은 변경하지 않음

보장 조건:

- 같은 사용자의 시작 요청 두 개가 동시에 들어와도 커밋 후 진행 중 일반 문제풀이 세션은 1개
- 새 세션 또는 풀이 기록 생성 실패 시 기존 세션과 임시 답안 유지
- 다른 사용자의 시작 요청은 서로 막지 않음
- 예정일이 아니거나 종료 상태인 계획 블록으로는 새 세션이 생성되지 않음
- 계획 재생성 뒤 원본 계획이 보관되어도 기존 진행 세션 제출은 정상 완료되고 원본 계획 블록에 반영됨

## 4. diagnosis 필수 요청 1 — 진행 중 목록 GET의 삭제 제거

대상: `app/diagnosis/views.py`의 진행 중 평가 목록 함수(`diagnosis_in_progress_sessions`)

현재 GET 요청이 진행 중 진단 세션을 조회한 뒤 최신 1개를 제외한 나머지를 삭제한다. 이 조회는 평가 구분을 나누지 않아 일반 진단평가와 주간평가 중 하나가 삭제될 수 있다.

요청 사항:

- GET 요청에서 세션을 삭제하지 않음
- 일반 진단평가와 주간평가를 평가 구분(`review_type`)별로 조회
- 각 유형의 최신 진행 세션을 최대 1개씩 응답
- 각 응답 항목에 평가 구분(`reviewType`)을 포함해 화면이 일반 진단과 주간평가를 구별할 수 있게 함
- 기존 중복 세션이 발견되어도 조회 중 자동 삭제하지 않고 로그·점검 대상으로만 남김
- 조회 전후 `solve_sessions`, `solve_records` 변화 0건 보장

사용자 안내 문구:

> 진행 중인 풀이는 유형별로 최대 1개만 보관됩니다. 새 풀이를 시작하면 같은 유형의 기존 풀이가 삭제됩니다.

## 5. diagnosis 필수 요청 2 — 새 평가 교체·블록 검증·보관 계획 완료

대상: `app/diagnosis/views.py`의 진단평가 시작 함수(`diagnosis_start`)

현재 같은 평가 유형의 진행 세션을 삭제한 뒤 새 세션과 문항을 생성한다. 삭제 뒤 생성 과정이 실패하면 기존 이어풀기 데이터만 잃을 수 있으므로 교체 작업 전체를 한 트랜잭션으로 묶어 달라.

요청 처리 순서:

1. 사용자와 평가 유형 확인
2. 한 트랜잭션 시작
3. 사용자 행을 `SELECT ... FOR UPDATE`로 잠금
4. 계획 주간평가이면 analytics 호환 창구의 계획 블록 시작 검증 함수(`validate_study_plan_block_start`)로 활성 계획 소유권·실행 경로·예정일·풀이 기록을 반영한 블록 상태 검증
5. 같은 사용자·같은 평가 유형의 진행 세션 재조회
6. 기존 세션 삭제
7. 새 평가 세션 생성
8. 새 세션의 전체 풀이 기록 생성
9. 모두 성공한 경우에만 커밋

보장 조건:

- 일반 진단평가를 시작해도 주간평가 세션은 삭제되지 않음
- 주간평가를 시작해도 일반 진단평가 세션은 삭제되지 않음
- 새 세션 또는 풀이 기록 생성 실패 시 기존 세션과 임시 답안 유지
- 성공 후 해당 평가 유형의 진행 세션은 1개
- 계획 주간평가의 예정일이 `Asia/Seoul` 기준 오늘이 아니면 `409 BLOCK_NOT_DUE`, 완료·놓침·취소 상태이면 `409 BLOCK_TERMINAL`로 새 세션 생성을 차단
- 기존 진행 세션 이어풀기는 새 시작 검증과 분리하고 원본 계획이 보관 상태여도 기존 세션·문제·임시 답안을 반환
- 기존 주간평가 세션 제출 완료 시 풀이 기록에 연결된 원본 계획이 활성 또는 보관 상태이면 기존 analytics 블록 완료 함수를 호출하고, diagnosis 내부의 활성 계획 전용 사전 조회 때문에 호출을 생략하지 않음

일반 진단평가와 주간평가 시작은 모두 사용자 → 세션 순서로 잠가 동시 시작을 직렬화한다.

## 6. diagnosis 필수 요청 3 — 제출 잠금·전체 문항 검증

대상: `app/diagnosis/views.py`의 진단평가 제출 함수(`diagnosis_submit`)

현재 제출 경로는 세션 행을 잠그지 않고, 제출 문항 번호가 세션 전체 문항 번호와 같은지도 검증하지 않은 채 세션을 완료한다. analytics는 호출된 이후의 블록 완료·리포트 등록은 멱등하게 만들 수 있지만, 그 전에 발생하는 답안 경합과 일부 문항 제출 완료를 복구할 수 없다.

요청 처리 순서:

1. 한 트랜잭션 시작
2. 사용자·세션 유형과 함께 세션 행을 `SELECT ... FOR UPDATE`로 조회
3. 이미 완료된 세션이면 기존 중복 제출 응답 반환
4. 세션의 전체 풀이 기록을 잠그고 문항 번호 집합 조회
5. 제출 문항 번호의 중복이 없고 세션 문항 번호 집합과 정확히 일치하는지 검증
6. 답안·점수·세션 완료·분석 스냅샷 저장
7. 기존 analytics 블록 완료 함수 호출
8. 모두 성공한 경우에만 커밋

미응답 선택지(`choice_id=null`)는 오답으로 제출할 수 있지만 문항 번호 자체는 전체 세션 목록에 포함되어야 한다.

보장 조건:

- 일부 문항 누락, 세션에 없는 문항, 중복 문항이 있으면 세션·풀이 기록·블록·리포트 변화 0건
- 동시에 같은 세션을 제출해도 완료·블록 반영·리포트 등록 효과는 한 번
- analytics 호출 실패 시 세션과 답안 완료도 함께 롤백
- 기존 제출 요청·응답 필드와 analytics 완료 함수 호출 형식은 유지

## 7. question·diagnosis 공통 요청 — 학습일을 서울 기준으로 통일

대상: question·diagnosis에서 신규 `SolveSessions`를 생성하는 모든 경로

공용 학습일 기준은 `Asia/Seoul`로 확정한다.

요청 사항:

- 신규 세션의 학습일(`recorded_date`)은 세션 생성 시각을 `Asia/Seoul`로 변환한 현지 날짜로 저장
- 서버의 현지 날짜인 `date.today()`나 UTC 날짜를 직접 저장하지 않음
- 일반 문제풀이, 학습계획 문제풀이, 일반 진단평가, 주간평가에 같은 규칙 적용
- 세션이 서울 자정을 넘어 제출되더라도 생성 시 저장한 학습일은 변경하지 않음
- 생성·수정 시각 같은 시각형 필드는 기존 UTC 저장 방식을 유지
- 기존 `recorded_date`는 정확한 원시 시각을 복원할 수 없으므로 일괄 수정하지 않음
- 적용 배포 시각을 기록하고 전환 이후 신규 세션부터 동일 기준 적용

보장 조건:

- 같은 실제 시각에 생성된 question·diagnosis 세션의 학습일이 동일함
- 서울 자정 직전과 직후 생성한 세션의 학습일이 각각 기대 날짜로 저장됨
- 조회 기간 집계와 주간 비교가 서울 달력 날짜를 기준으로 동작함

## 8. analytics에서 처리하는 항목

- 기존 계획 JSON 형식과 현재 조회 경로 유지
- 새 세션 생성 전 공통 판정을 위한 읽기 전용 계획 블록 시작 검증 함수(`validate_study_plan_block_start`)를 기존 analytics 호환 창구에 제공
- 기존 블록 완료 함수의 내부 검증·멱등성 강화
- 제출 호출자가 이미 세션을 잠갔을 수 있으므로 완료 함수는 사용자 행을 추가로 잠그지 않고 전달된 활성 또는 보관 계획 행만 잠금
- 풀이 기록의 계획·블록 연결로 완료된 주간평가 세션 확인
- 원본 평가 세션 번호를 리포트 JSON에 저장
- 리포트 대기 등록과 중복 세션 충돌 방지
- 제출 완료 후 리포트 등록이 누락된 경우 작업 처리기가 복구
- 다음 계획 자동 생성·보류·마이페이지 동기화 시 보류 재확인
- 관계 수준 개인화 활성화 뒤 기존 풀이 기록·문제·선택지를 조인해 정답·사용자 선택 선택지 후보 추출
- Neo4j 재설계 뒤 analytics resolver에서 선택지와 문제 문맥을 직접 검색해 반복 혼동 근거 계산. 사용자 풀이 이력의 Neo4j 적재와 RAG·pgvector 검색은 하지 않음

따라서 다음 변경은 question·diagnosis에 요청하지 않는다.

- analytics 공용 조회기(resolver)로의 즉시 전환
- diagnosis 내부 계획 JSON 조회 함수 제거
- analytics 완료 함수에 새 매개변수 추가
- 제출 API 전체 구조 개편
- 리포트·작업 신규 테이블
- 취소 사유 필드
- 문제·선택지의 Neo4j Entity 연결 열

## 9. 완료 확인 시나리오

1. 일반 문제풀이 동시 시작 요청 후 진행 중 세션이 정확히 1개다.
2. 일반 진단평가와 주간평가가 각각 진행 중인 상태에서 목록 GET을 호출해도 두 세션이 유지된다.
3. diagnosis 목록 응답의 평가 구분으로 두 세션을 구별할 수 있다.
4. 목록 GET 전후 세션·풀이 기록 수와 저장 답안이 변하지 않는다.
5. 새 일반 진단평가를 시작하면 기존 일반 진단평가만 교체되고 주간평가는 유지된다.
6. 새 주간평가를 시작하면 기존 주간평가만 교체되고 일반 진단평가는 유지된다.
7. 새 세션 생성 또는 풀이 기록 생성에 실패하면 기존 이어풀기 데이터가 유지된다.
8. 같은 유형의 새 평가 시작이 성공하면 진행 세션이 정확히 1개다.
9. 서울 자정 경계 전후에 생성한 question·diagnosis 세션의 학습일이 같은 기준으로 저장된다.
10. 미래·과거 예정일 또는 완료·놓침·취소 계획 블록으로 새 풀이를 시작하면 세션과 풀이 기록이 생성되지 않는다.
11. 계획 재생성으로 원본 계획이 보관된 뒤 기존 question·diagnosis 진행 세션을 이어풀어 제출하면 원본 보관 계획의 블록에 완료가 반영되고 새 활성 계획에는 반영되지 않는다.
12. diagnosis에 일부·중복·다른 세션 문항 목록을 제출하면 세션과 데이터가 변경되지 않는다.
13. 같은 diagnosis 세션을 동시에 제출해도 완료·블록·리포트 등록 효과는 한 번이다.

## 10. 개발 병행과 운영 활성화 조건

analytics의 계획·JSON·동기화와 리포트 작업 처리기 개발은 본 요청의 적용을 기다리지 않고 병행한다.

다만 다음 조건을 모두 확인하기 전에는 연동 E2E를 완료 처리하거나 학습계획·주간리포트 기능을 운영에서 활성화하지 않는다.

- question 시작 사용자 잠금 적용
- diagnosis 진행 중 목록 GET의 삭제 제거
- diagnosis 같은 평가 유형 교체의 사용자 잠금·트랜잭션 적용
- diagnosis 제출의 세션 잠금·전체 문항 검증·단일 트랜잭션 적용
- question·diagnosis의 계획 블록 새 시작 예정일·종료 상태 검증 적용
- question·diagnosis의 보관 계획 연결 세션 제출 완료 전달 적용
- question·diagnosis 신규 세션의 서울 기준 학습일 적용
- 연동 환경에서 조회·새로 시작·제출 시 세션과 임시 답안 유실 0건 확인

특히 diagnosis GET 삭제가 남아 있는 상태에서는 화면 조회만으로 진행 세션이 사라질 수 있으므로 운영 활성화를 금지한다.

관계 수준 개인화는 Neo4j 재설계와 analytics resolver 검증 뒤 별도로 활성화한다. 기존 집계 기반 리포트의 운영 활성화를 막지 않는다.

## 11. 요청하지 않는 선택 항목

- 주간평가 고정 비율 출제 기준 변경
- 오답 우선 재출제 정책
- 문제 생성의 동일 경로 오답 후보 선정 알고리즘 변경
- 문제·선택지의 Neo4j Entity 연결 열 추가
- RAG·pgvector·임베딩 검색 도입
- question·diagnosis 화면 전체 개편

## 12. 담당 회신 요청

- question 시작 잠금·블록 검증·보관 계획 완료 전달, diagnosis GET 삭제 제거·안전한 평가 교체·제출 잠금·전체 문항 검증·블록 검증·보관 계획 완료 전달, 공용 서울 기준 학습일 적용 가능 여부
- 동시 시작 요청을 막는 현재 잠금 방식 유무
- 영향받는 API와 테스트
- 연동 가능한 일정
