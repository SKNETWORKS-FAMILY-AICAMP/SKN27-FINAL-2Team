# 주간평가 식별·세션 보존·리포트 연동 — 협조 요청서 (diagnosis / question 앱)

> 문서 상태: SUPERSEDED COORDINATION NOTE
> 초기 협조 범위 참고용이다. 실제 구현 계약은 [study_plan/CONTRACTS.md](study_plan/CONTRACTS.md)와 [study_plan/AI_WORKFLOW.md](study_plan/AI_WORKFLOW.md)를 따른다.

`docs/mypage/study_plan/AI_WORKFLOW.md`(주간 AI 리포트)와
`docs/mypage/study_plan/SPEC.md`(이월·미응시·상태 분기)의 구현이
analytics 앱 밖의 변경을 필요로 한다. 범위 밖 6건을 아래와 같이 담당자 반영을 요청한다.

**전제 — DB 선행 요청** (DB 담당자에게 별도 진행, 적용 후 요청 1~4 배포 가능):

- `init.sql`: `solve_sessions` CREATE TABLE 안에 아래 컬럼 직접 추가,
  `alter_apply_latest.sql`: `ADD COLUMN IF NOT EXISTS` 형태로 동일 반영
  - `review_type VARCHAR(20) NULL` — NULL(일반) | 'weekly_review'(주간평가),
    허용값 CHECK 포함
  - `cancelled_at TIMESTAMP NULL` — 타입은 기존 solve_* 계열 관례(TIMESTAMP)에 맞추되 DB 담당 확인
  - `cancellation_reason VARCHAR(20) NULL` — 허용값 CHECK: `'user_cancel'` (초기 1종, NULL 허용)
- 주간평가 조회용 partial index (`DB_스키마_변경_요청서.md`의 solve_sessions 구문 참조)
- `study_plan_mypage` active 유일성 partial unique index (`study_plan/SPEC.md` 4.1장, `DB_스키마_변경_요청서.md` 참조)
- `solve_sessions.status`에는 CHECK 제약이 없으므로 `'cancelled'` 값 추가 자체는 스키마 변경 불필요

## 현재 구현 상태 (이미 반영된 것 — 재작업 불필요)

혼선 방지를 위해 이미 구현돼 있는 부분을 먼저 명시한다.

- `DiagnosisStartRequestSerializer`에 `studyplan_id`, `study_plan_block_id` 필드 존재
- `diagnosis_start`의 주간평가 블록 검증 (`_find_weekly_review_block` — active 계획 조회,
  blockId 매칭, `weekly_review` 타입 확인)
- 세션 시작 시 `SolveRecords`에 `studyplan_id`, `study_plan_block_id` 저장
  (진단평가는 시작 시 빈 records를 만들어 이어풀기를 지원하는 구조)
- 제출 완료 시 블록 완료 처리 (`_complete_weekly_review_block_for_session` →
  `complete_study_plan_block_by_id`, 멱등)

즉 "record 연결값" 경로는 완성돼 있고, 빠져 있는 것은 **세션 단위 식별자(`review_type`),
진행 중 세션 보존·취소 정책,
리포트 작업 enqueue, 출제 방식**이다.

## 요청 1. `SolveSessions` 모델 컬럼 선언 (question 앱)

### 배경

주간평가는 진단평가 API로 실행되므로 세션 데이터만으로는 일반 진단평가와 구분되지 않는다
(`session_type='diagnostic'`, `status='completed'` 동일). 현재는 record의
`studyplan_id`/`study_plan_block_id` 존재 여부로 간접 추정하는데, 최신 설계는
`SolveSessions.review_type='weekly_review'`를 1차 식별 기준으로 확정했다
(`study_plan/AI_WORKFLOW.md` 5장). 이 식별자가 있어야 analytics가
주간평가 완료/미응시 분기, 리포트 비교 대상 선택, 오늘 계획 공백 복구를 구현할 수 있다.

### 요청 내용

`app/question/models.py`의 `SolveSessions`에 컬럼을 선언한다
(모델이 `managed=False`이므로 DB ALTER와 별개로 모델 선언이 있어야 ORM이 읽는다).
취소 필드(요청 4)도 함께 선언한다.

```python
review_type = models.CharField(max_length=20, blank=True, null=True)
cancelled_at = models.DateTimeField(blank=True, null=True)
cancellation_reason = models.CharField(max_length=20, blank=True, null=True)
```

- `review_type` 값: `NULL`(일반 세션) | `'weekly_review'`(주간평가). 다른 값은 현재 없다.
- 기존 데이터는 NULL 유지. 과거 주간평가는 record 연결값 fallback으로 식별한다
  (analytics 측에서 처리, "제공 사항" 참조).

## 요청 2. 주간평가 세션에 `review_type` 저장 (diagnosis 앱)

### 요청 내용

1. `diagnosis_start`에서 주간평가 블록 검증(`weekly_review_block`)을 통과한 요청은
   세션 생성 시 `review_type='weekly_review'`를 저장한다.

```python
session = SolveSessions.objects.create(
    ...,
    review_type="weekly_review" if weekly_review_block else None,
)
```

2. 일반 진단평가 세션은 `review_type=None`으로 저장한다 (기본값이므로 변경 없음).
3. record의 `studyplan_id`/`study_plan_block_id` 저장은 현행 유지 —
   블록 연결·진행률 계산의 보조 기준으로 계속 쓴다.

## 요청 3. 학습계획 연결 진행 중 세션 보존·이어풀기 (diagnosis / question 앱)

### 배경

현재 새 세션 시작 시 기존 `in_progress` 세션을 일괄 삭제한다.

- diagnosis: `diagnosis_start`가 사용자의 `session_type='diagnostic'` + `in_progress`
  세션을 전부 삭제 (diagnosis/views.py 197행 부근)
- question: `_delete_other_in_progress_sessions`가 practice `in_progress` 세션과
  records를 전부 삭제 (question/views.py 141행 부근)

학습계획에 연결된 세션이 삭제되면 진행 중 답안이 유실되고 이어풀기가 무력화된다.
`review_type`으로 삭제 범위를 나눠도 같은 종류(주간평가↔주간평가, 학습계획
practice↔practice) 간 삭제는 남으므로 연결 세션 보존 정책이 별도로 필요하다.

### 요청 내용 (diagnosis·question 공통 정책)

1. `SolveRecords.studyplan_id` + `study_plan_block_id`가 연결된 `in_progress` 세션은
   자동 삭제하지 않는다.
2. **같은 plan·block**의 세션이 이미 진행 중이면 새 세션을 만들지 않고
   기존 `session_id`와 이어풀기 정보를 반환한다.
3. **다른 plan·block**의 연결 세션이 진행 중이면 임의 삭제하지 않고
   `409 ACTIVE_SESSION_EXISTS`와 기존 `session_id`를 반환한다.
   사용자가 기존 세션을 완료하거나 명시적으로 취소(요청 4)한 뒤 새로 시작한다.
4. 미연결 임시 세션의 자동 정리는 유지하되, 같은 `session_type`·`review_type`
   범위에서만 수행한다 (일반 진단평가 시작이 진행 중 주간평가 세션을 지우지 않게).

> 후속 보강: review_type 필터만으로는 같은 종류의 plan 연결 세션 삭제가 남는다.
> studyplan_id·study_plan_block_id가 연결된 in_progress session은 삭제하지 말고 기존 session을 반환해 이어풀기해야 한다. 같은 원칙을 question 앱의 practice session 정리에도 적용한다.
> 완료 불가능한 세션의 영구 BLOCKED를 막기 위한 cancelled 상태·보존형 취소 API는 별도 협조·승인 항목이다.

## 요청 4. 삭제 없는 명시적 취소 (diagnosis / question 앱)

### 배경

요청 3으로 연결 세션의 자동 삭제가 사라지면, 사용자가 진행 중 세션을 버리고
새로 시작할 수 있는 명시적 경로가 필요하다. DELETE는 답안 기록을 유실시키므로
상태 전환(`cancelled`)으로 처리한다.

### 요청 내용

취소 API:

- diagnosis: `POST /diagnosis/api/session/{session_id}/cancel/`
- question: `POST /question/api/session/{session_id}/cancel/`

처리 규칙:

1. 로그인 사용자 소유의 `in_progress` 세션만 취소할 수 있다.
2. 완료된 세션은 취소할 수 없다.
3. 취소 시 `status='cancelled'`, `cancelled_at=NOW()`,
   `cancellation_reason='user_cancel'`을 저장한다.
4. `SolveRecords`와 기존 답안은 DELETE하거나 다른 block으로 재연결하지 않는다 (보존).
5. **연결된 학습계획 블록은 변경하지 않는다.** 블록은 미완료로 남아 그대로 재시작
   가능하다(`canStart` 정책). 블록에 별도 취소 상태를 만들지 않는다.
6. 중복 취소 요청은 기존 취소 결과를 반환하는 멱등 처리로 한다 (상태 변화는 1회만).
7. 취소 과정에서 active 계획을 archive하거나 AI 에이전트를 직접 실행하지 않는다.

### 파급 안전 (확인된 사항 — 추가 작업 불필요)

- 통계·취약점 집계는 `status='completed'` 필터를 쓰므로 cancelled 세션은 자동 제외된다.
- 리포트 enqueue는 제출(completed) 시점에만 발생하므로 취소(in_progress 한정)와
  경합하지 않는다.

## 요청 5. 제출 완료 시 주간 리포트 작업 enqueue (diagnosis 앱)

### 배경

주간평가 제출이 AI 리포트 생성의 트리거다. 제출 API는 리포트를 직접 만들지 않고
작업 row만 등록하며, 생성은 analytics 백그라운드 worker가 담당한다.

### 요청 내용

`diagnosis_submit` 완료 처리에 다음을 추가한다.

1. enqueue 조건: 해당 세션이 `review_type='weekly_review'`이고 `status='completed'`.
2. analytics가 제공하는 enqueue 서비스 함수를 **제출 트랜잭션 안에서** 호출한다.
   함수 내부가 `(user_id, session_id)` 기준 upsert(`ON CONFLICT DO NOTHING`)라
   중복 제출·재시도에 멱등하다.
3. record 연결값(`studyplan_id`)이 있으면 `source_studyplan_id`로 전달하고,
   없으면 NULL로 enqueue는 유지한다 (블록 완료 처리만 건너뜀 — 현행 로직과 동일).
4. worker 알림은 함수 내부에서 `transaction.on_commit()`으로 등록된다.
   제출 API는 호출만 하면 되고, 커밋 전 알림·직접 실행을 추가하지 않는다.

### 금지 사항 (설계 확정)

- 제출 API는 Collector/Analyst/Recommender/Writer/Planner를 **직접 실행하지 않는다**.
- 제출 API는 기존 active 학습계획을 **archived 처리하지 않는다**
  (리포트 `READY` 이후 analytics worker가 Planner를 자동 실행하고 finalize 트랜잭션에서 교체).
- 이미 `READY`/`RUNNING`인 리포트 row를 `PENDING`으로 되돌리지 않는다 (함수 내부 보장).

### 시점 의존성

`weekly_ai_reports` 테이블과 enqueue 함수는 analytics 구현 범위다.
analytics가 함수를 제공하기 전에는 이 요청을 반영할 수 없으므로,
요청 1~4를 먼저 반영하고 요청 5는 analytics 측 준비 완료 통보 후 반영한다.

## 요청 6. 주간평가 출제를 고정 비율 종합평가로 변경 (diagnosis 앱)

### 배경

현재 `_pick_diagnosis_question_ids()`는 전체 문제에서 50문항/100점 조합을
완전 무작위로 뽑는다. 주간평가의 목적은 진단평가·지난 주간평가 대비
**시점 간 정답률 비교**인데, 매회 문항 분포(시대·주제·유형·난이도)가 다르면
점수 변화가 실력 변화인지 출제 분포 차이인지 구분할 수 없다.

취약점 기반 출제로 바꾸는 것이 아니다 — 취약 문제만 내면 분포가 더 왜곡된다.
취약 판정은 평가 **후** 분석·다음 계획 생성에 쓰이고(설계 확정), 출제는 분포가
고정된 종합평가여야 한다 (`study_plan/SPEC.md` 11장 주간평가).

### 요청 내용

1. 문항 선택을 시대·주제·유형·난이도 **비율 고정** 방식으로 변경한다.
   비율 값은 하드코딩하지 말고 설정 함수/상수 모듈 한 곳에서 관리한다.
2. 구체 비율 값은 기획 협의 사항이다. 초기값 협의 시 analytics 측과
   시대·유형 분포 기준을 맞춘다 (판정 집계 단위와 동일한 분류 체계 사용).
3. 일반 진단평가와 주간평가가 같은 선택 로직을 쓰는 현행 구조는 유지한다 —
   둘의 분포가 같아야 "진단 대비 변화" 비교가 성립한다.

## 제공 사항 (analytics 측)

- `complete_study_plan_block_by_id()` — 이미 제공·사용 중 (멱등)
- enqueue 서비스 함수 (요청 5) — `weekly_ai_reports` 구현 시 제공 예정.
  시그니처는 `(user_id, session_id, source_studyplan_id=None)` 형태로 협의
- `review_type` 도입 전 과거 데이터 fallback — analytics 내부에서 처리
  (완료된 diagnostic 세션 중 record 연결값이 있는 최신 1건, `study_plan/AI_WORKFLOW.md` 8장 비교 baseline 선택 규칙)
- 취소된 세션은 analytics 집계에 파급이 없음을 확인 완료 (별도 처리 불필요)

## 검증 시나리오

1. 주간평가 블록에서 시작 → 세션 `review_type='weekly_review'`, records에 연결값 저장
2. 일반 진단평가 시작 → `review_type` NULL
3. 같은 plan·block을 다시 시작 → 새 세션 없이 기존 `session_id`와 이어풀기 정보 반환
4. 일반 진단평가 시작이 진행 중 주간평가 세션을 삭제하지 않음
5. 다른 plan·block의 연결 세션이 진행 중 → `409 ACTIVE_SESSION_EXISTS` + 기존 `session_id`
6. 취소 후 → 세션 `cancelled`·`cancelled_at` 저장, records 보존,
   블록은 미완료 유지로 즉시 재시작 가능
7. 같은 취소 요청 반복 → 상태 변화 없이 기존 취소 결과 반환 (멱등)
8. 완료된 세션 취소 → 거부
9. 주간평가 제출 → 블록 `isCompleted=true` + `weekly_ai_reports`에 `PENDING` row 1개,
   중복 제출 시 row 불변 (요청 5 반영 후)
10. 주간평가 2회 반복 → 문항의 시대·유형 분포가 동일 비율 (요청 6 반영 후)

## 일정 의존성

```text
DB: review_type · cancelled_at · cancellation_reason 컬럼 + 인덱스 (DB 담당, 선행)
  → 요청 1 (모델 선언) → 요청 2 (review_type 저장)
  → 요청 3 (세션 보존·이어풀기) + 요청 4 (명시적 취소) — 3·4는 한 묶음으로 반영
      (보존만 먼저 넣으면 사용자가 진행 세션을 버릴 방법이 없어진다)
  → analytics: weekly_ai_reports 테이블·worker·enqueue 함수 구현
      → 요청 5 (제출 enqueue)
요청 6 (고정 비율 출제)은 위와 독립 — 비율 협의 후 언제든 반영 가능
```
