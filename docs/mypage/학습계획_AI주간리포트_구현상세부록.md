## 1. 취약점 분석과 계획 계산

### 1.1 분석과 계획의 범위 분리

취약점 상세분석은 사용자가 결과를 탐색할 수 있도록 다음 단위를 계산할 수 있다.

- 시대
- 주제
- 문제 유형
- 시대+주제
- 시대+주제+유형

실제 기록이 존재하는 조합만 계산한다. 가능한 조합 전체를 미리 만들지 않는다.

계획 계산기는 위 결과를 모두 소비하지 않는다.

| 용도 | 사용 단위 |
|---|---|
| 개인화 계획 기본 후보 | 시대+주제 |
| 문항 부족 시 완화 | 시대 |
| 첫 주 4일차 | 유형 단일 축 |
| 취약점 화면·리포트 설명 | 전체 분석 단위 |

이 구분으로 취약점 화면의 상세도는 유지하면서 계획 후보·폴백·문항 검증은 두 단계로 제한한다.

### 1.2 분석 대상 기록

- 기준일: 계획 생성 또는 리포트 수집 시점의 `Asia/Seoul` 달력 날짜
- 조회 기간: 최근 90일
- 포함: 정상 완료된 일반 문제풀이, 일반 진단평가, 주간평가의 제출 답안
- 제외: 진행 중·삭제 세션, 미제출 답안, 정답 여부를 판단할 수 없는 기록
- 기록일(`recordedDate`) 해석: 날짜형 열에 저장된 값을 그대로 사용한다. 전환 이후 신규 세션은 생성 시각을 `Asia/Seoul`로 변환해 이 날짜를 저장하며, 원시 시각이 없는 기존 날짜는 재해석하거나 보정하지 않는다.

한 요청에서 조회한 기록과 계산 결과는 취약점 화면·계획 후보·리포트 분석이 함께 재사용한다. 초기에는 별도 캐시를 만들지 않고 쿼리 횟수와 처리시간을 관측한다.

### 1.3 최근성 가중치

```text
최근성 가중치(decayWeight)
= 0.5 ^ (경과 일수(daysAgo) / 반감기 일수(halfLifeDays))

가중 전체 표본(effectiveTotal)
= Σ 최근성 가중치(decayWeight)

가중 오답 표본(effectiveWrong)
= Σ 최근성 가중치(decayWeight) × 오답 여부(isWrong)
```

초기 설정:

| 설정 | 값 |
|---|---:|
| 조회 기간(`lookbackDays`) | 90일 |
| 반감기(`halfLifeDays`) | 14일 |
| 최소 유효 표본(`minimumEffectiveSample`) | 3.0 |
| 신뢰 계수(`wilsonZ`) | 1.28 |

오늘·14일 전·28일 전 기록의 가중치는 각각 `1`, `0.5`, `0.25`다. 모든 값은 버전 설정에서 관리한다.

### 1.4 Wilson 취약 점수

```text
가중 오답률(pHat) = effectiveWrong / effectiveTotal
유효 표본(n) = effectiveTotal

취약 점수(weaknessScore)
= (
    pHat + z²/(2n)
    - z × sqrt((pHat × (1-pHat) / n) + z²/(4n²))
  ) / (1 + z²/n)
```

- 표본이 적은 높은 오답률을 그대로 취약으로 단정하지 않기 위해 오답률의 Wilson 하한을 사용한다.
- 유효 표본이 `0`이면 점수를 계산하지 않는다.
- 유효 표본이 `3.0` 미만이면 점수는 참고값으로만 두고 판정은 표본 부족(`INSUFFICIENT`)이다.

| 조건 | 판정 |
|---|---|
| 유효 표본 3.0 미만 | 표본 부족 |
| 취약 점수 0.50 이상 | 취약 |
| 취약 점수 0.20 이하 | 안정 |
| 그 사이 | 중립 |

표본 부족이면서 실제 오답이 있으면 화면에 후보 신호로 표시한다. 오답이 없으면 목록에서 제외한다.

### 1.5 추세

최근 14일과 직전 14일을 각각 **구간 내 균등 가중치**로 계산한다. 최근성 감쇠는 현재 취약 상태를 추정할 때만 사용하고, 추세 비교 구간 안에서는 사용하지 않는다.

```text
추세 차이(trendDelta)
= 최근 취약 점수(recentWeaknessScore)
  - 직전 취약 점수(previousWeaknessScore)
```

| 차이 | 추세 |
|---|---|
| `+0.10` 이상 | 악화(`worsening`) |
| `-0.10` 이하 | 개선(`improving`) |
| 그 사이 | 유지(`flat`) |
| 어느 한쪽 표본 부족 | 불명(`unknown`) |

추세는 독립 취약 상태가 아니라 화면 배지다. 계획 점수에 보너스나 감점을 넣지 않고 동률 정렬에만 사용한다.

### 1.6 단일 취약 정의와 화면별 역할

취약 점수(`weaknessScore`)는 “최근성과 표본 수를 보정한 현재 오답률” 하나로 정의한다. 풀이시간·시험 중요도·반복 오답을 취약 점수에 섞지 않는다.

- “현재 취약한가”는 취약 점수와 상태(`status`)가 답한다.
- “이번 기간에 몇 문제를 틀렸는가”는 원시 오답 수·오답률(`rawWrongCount`, `rawWrongRate`)이 답한다.
- “무엇을 먼저 공부할 것인가”는 계획 우선순위(`priorityScore`)가 답한다.

세 질문의 값을 하나의 점수나 라벨로 섞지 않는다.

| 사용처 | 집계 단위 | 목록·정렬 | 사용자 표시 |
|---|---|---|---|
| 마이페이지 취약 목록 | 시대+주제 | 현재 상태가 취약인 항목만, 취약 점수 내림차순 | 순위, 취약 배지, `N문제 중 M오답`, 숫자 없는 막대 |
| 오답률 상세의 기간 목록 | 시대·주제·유형 | 화면 기간의 원시 오답률 내림차순 | 원시 오답률·개수, 현재 취약 배지와 추세 |
| 세션 상세 모달 | 해당 세션의 분류 | 원시 오답률·오답 수 | `세션 오답 TOP`, 취약 판정 문구 사용 안 함 |
| 기간 상세 모달 | 선택 기간의 분류 | 원시 오답률·오답 수 | `기간 오답 TOP`, 취약 판정 문구 사용 안 함 |
| 학습계획 | 시대+주제, 부족하면 시대 | 계획 우선순위 | 계획 이유만 표시 |
| AI 주간리포트 | 필요한 상세 분석 단위 | 결정 코드가 고른 근거 순 | 좋아진 영역·보완 영역과 근거 문항 수 |

마이페이지 취약 목록은 중립(`NEUTRAL`)과 표본 부족(`INSUFFICIENT`)을 섞지 않는다. 목록이 비면 “아직 취약으로 판단할 데이터가 부족해요. 문제를 더 풀면 분석이 정확해져요.”를 표시한다.

학습계획 후보는 화면 목록보다 넓게 잡는다. 취약 또는 중립이면서 취약 점수가 안정 임계값보다 큰 시대+주제를 후보로 허용한다. 안정과 표본 부족은 개인화 취약 후보에서 제외한다. 후보가 없으면 1.14의 폴백을 사용한다.

개선(`improving`)·악화(`worsening`)는 상태가 아니라 배지다. 예를 들어 취약+개선, 중립+악화가 모두 가능하다.

### 1.7 분석 결과 계약

분석 행 하나는 판정용 값과 표시용 원시 값을 함께 가지되 역할을 구분한다.

```json
{
  "groupKeyId": "era=%EA%B7%BC%ED%98%84%EB%8C%80|topic=%EC%82%AC%ED%9A%8C",
  "groupKey": {
    "era": "근현대",
    "topic": "사회"
  },
  "label": "근현대 · 사회",
  "raw": {
    "total": 20,
    "wrong": 14,
    "wrongRate": 0.7
  },
  "effective": {
    "total": 16.2,
    "wrong": 11.9
  },
  "weaknessScore": 0.558,
  "status": "WEAK",
  "trend": "worsening",
  "trendDelta": 0.18,
  "recentScore": 0.61,
  "previousScore": 0.43
}
```

- 계산은 반올림하지 않은 값으로 수행한다.
- JSON 직렬화와 화면 표시에만 설정된 자릿수를 적용한다.
- 원시 오답률(`raw.wrongRate`)은 표시·기록용이고 상태 판정에는 사용하지 않는다.
- 취약 점수(`weaknessScore`)는 판정·마이페이지 정렬·계획 입력용이다.
- 추세 구간 한쪽이 표본 부족이면 추세 차이와 두 구간 점수는 `null`, 추세는 `unknown`이다.
- 표시 이름(`label`)은 식별자로 사용하지 않는다.

### 1.8 영역 식별자와 분류값

분석 결과·계획·리포트가 같은 영역을 가리키도록 영역 식별자(`groupKeyId`)를 사용한다.

- 필드 순서는 시대(`era`) → 주제(`topic`) → 유형(`qType`)으로 고정한다.
- 원본 분류값은 앞뒤 공백과 서비스가 정한 별칭만 분류 모듈에서 정규화한다.
- 값은 UTF-8 percent-encoding 후 `field=value` 형태로 만들고 `|`로 연결한다.
- `|`, `=`, `%`, 공백이 포함된 값도 충돌하거나 파싱이 깨지지 않아야 한다.
- 미분류 값의 내부 표현과 화면 표시명은 분리한다.
- 식별자 생성·파싱은 한 모듈에서만 수행하고 화면별로 문자열을 직접 조립하지 않는다.

예시:

```text
era=%EA%B7%BC%ED%98%84%EB%8C%80|topic=%EC%82%AC%ED%9A%8C
era=%EC%A1%B0%EC%84%A0|topic=a%3Db%7Cc|qType=%EC%82%AC%EB%A3%8C
```

분류 표시명은 버전 설정 또는 분류 모듈에서 관리한다. 알 수 없는 값은 삭제하지 않고 안전한 미분류 표시로 보존한다.

### 1.9 현재 판정 경로와 원시 기록 경로

저장된 analytics 스냅샷에는 날짜별 풀이 분포가 없어 최근성 감쇠와 추세를 다시 계산할 수 없다. 따라서 데이터 경로를 명시적으로 분리한다.

#### 경로 A — 현재 취약 판정

- 원천: 최근 90일 풀이 기록(`SolveRecords`)
- 사용처: 마이페이지 취약 목록, 오답률 상세 배지, 학습계획, AI 리포트
- 값: 유효 표본, Wilson 취약 점수, 상태, 추세

#### 경로 B — 원시 기록 표시

- 원천: 저장된 analytics 스냅샷 또는 선택 범위의 풀이 기록 재집계
- 사용처: 세션 결과, 세션·기간 모달, 기간 오답률 숫자와 차트
- 값: 실제 풀이 수, 오답 수, 원시 오답률

원시 기록 경로에 신규 취약 임계값을 적용하지 않는다. 반대로 현재 판정 경로에 과거 스냅샷의 원시 오답률을 섞지 않는다. 스냅샷에 취약 점수를 저장하는 방식도 채택하지 않는다. 설정이 바뀌었을 때 과거 저장 점수와 현재 판정이 조용히 달라지는 문제를 막기 위해서다.

오답률 상세 화면은 최근 7일 원시 집계에 존재하는 항목만 목록으로 유지하고, 90일 취약 분석은 그 항목의 배지에만 사용한다. 90일 기준 취약하지만 최근 7일에 풀지 않은 항목은 마이페이지 취약 목록에서 확인한다.

### 1.10 화면 표시 규칙

#### 마이페이지 취약 목록

- 취약 상태만 표시한다.
- 취약 점수 내림차순으로 정렬한다.
- 취약 점수와 원시 오답률 백분율은 숫자로 표시하지 않는다.
- 순위, 취약 배지, `N문제 중 M오답`, 취약 점수에 비례한 숫자 없는 막대를 표시한다.
- 막대 길이는 정렬과 단조 일치해야 하며 눈금·점수 라벨을 붙이지 않는다.
- 표본 부족 항목은 숨기고 목록 안내 문구로 설명한다.

#### 오답률 상세

- 숫자와 정렬은 선택 기간의 원시 오답률 기준으로 일치시킨다.
- 현재 취약 상태·판단 보류·추세는 별도 배지로 표시한다.
- “취약 배지는 최근 학습을 가중한 90일 기준”이라는 설명을 둔다.
- 도넛의 기타 묶음은 여러 영역의 합이므로 단일 취약 배지를 붙이지 않는다.
- 세션·기간 모달에는 취약이라는 단어 대신 오답 TOP 표현을 사용한다.

화면 문자 치환과 HTML escaping은 출력 단계에서 적용한다. 영역 표시명을 HTML로 신뢰하지 않는다.

### 1.11 구현·성능·캘리브레이션

취약 분석은 공용 서비스 `app/analytics/service/weakness.py`에 둔다.

기능 단위 공개 함수:

```text
설정 조회(getWeaknessConfig)
분석 행 생성(buildWeaknessRows)
상태 판정(determineWeaknessStatus)
추세 판정(determineTrend)
영역 식별자 생성(buildGroupKeyId)
```

- 매개변수에는 타입을 명시하고 설정값을 전역변수나 화면 코드에 하드코딩하지 않는다.
- Wilson 계산과 최근성 합산을 화면·계획·리포트에 복제하지 않는다.
- 분류 표시명은 `taxonomy.py`에서 관리한다.
- 한 요청에서는 최근 90일 기록 조회와 분석 결과를 재사용한다.
- 초기에는 DB 열이나 영구 캐시를 추가하지 않는다.
- 일 단위 그룹 집계 한 번으로 전체 기간·최근 구간·직전 구간을 함께 계산하는 것을 우선한다.
- 화면별 쿼리 수와 응답 시간을 측정하고 실제 지연이 확인될 때만 캐시를 설계한다.

초기 파라미터는 확정값이 아니라 배포 전 실데이터로 검증할 정책값이다.

1. 사용자별 실제 조합의 취약 점수 분포와 상태 비율을 확인한다.
2. 기존 raw 상위 목록과 신규 상위 목록을 나란히 검수해 소표본 100% 오답이 과대평가되지 않는지 본다.
3. 주간 추세가 과도하게 뒤집히는 비율을 확인하고 필요하면 추세 임계값을 조정한다.
4. 파라미터가 바뀌면 설정 버전을 올리고 리포트에 사용 버전을 남긴다.

캘리브레이션 스크립트는 서비스 코드와 분리한다. 운영 데이터 수정은 하지 않고 분포만 조회한다.

골든 케이스:

| 입력 | 기대 결과 |
|---|---|
| 오늘 1문제 중 1오답 | Wilson 약 0.379, 유효 표본 부족으로 `INSUFFICIENT` |
| 오늘 3문제 중 3오답 | Wilson 약 0.647, `WEAK` |
| 오늘 14문제 오답 / 20문제 | Wilson 약 0.56, `WEAK` |
| 60일 전 14문제 오답 / 20문제 | 유효 표본 약 1.0, `INSUFFICIENT` |
| 오늘 4문제 오답 / 20문제 | `STABLE` |
| 최근 점수 0.61, 직전 점수 0.43 | 차이 `+0.18`, `worsening` |
| 추세 구간 한쪽 유효 표본 2 | `unknown` |
| 분류값에 `|`, `=`, `%`, 공백 포함 | 식별자 생성·파싱 왕복 일치, 충돌 없음 |

### 1.12 시험 중요도와 반복 오답

시험 중요도(`examWeight`)는 시대+주제 계획 후보끼리, 또는 시대 폴백 후보끼리 따로 정규화한다.

```text
시험 중요도(examWeight)
= 해당 후보의 문제은행 문항 수(questionCount)
  / 같은 단계 후보 중 최대 문항 수(maxQuestionCount)
```

현재 값은 문제은행 분포를 이용한 임시 휴리스틱이며 실제 시험 출제 확률이나 AI 예측이 아니다. 공식 출제 비율을 받으면 출처 버전(`examWeightSourceVersion`)을 바꿔 교체한다.

반복 오답 신호(`repeatedError`)는 최근 세션을 가로질러 같은 영역을 반복해서 틀렸는지 나타낸다.

```text
반복 오답 신호(repeatedError)
= 오답이 한 개 이상 있었던 대상 세션 수(wrongSessionCount)
  / 해당 영역 답안이 있는 대상 세션 수(eligibleSessionCount)
```

- 최근 완료 세션 5개(`repeatWindowSessions`)까지만 본다.
- 대상 세션이 3개(`repeatMinimumSessions`) 미만이면 `0`이다.
- 같은 세션에서 여러 문항을 틀려도 한 번으로 센다.

### 1.13 계획 우선순위

```text
계획 우선순위(priorityScore)
= clamp(
    취약 가중치(weaknessWeight) × 취약 점수(weaknessScore)
    + 출제 가중치(examWeightRate) × 시험 중요도(examWeight)
    + 반복 가중치(repeatedErrorWeight) × 반복 오답 신호(repeatedError),
    0,
    1
  )
```

| 전략 | 남은 기간 | 취약 | 출제 | 반복 오답 |
|---|---|---:|---:|---:|
| 단기(`short`) | 7일 이하 | 0.40 | 0.45 | 0.15 |
| 중기(`medium`) | 8~21일 | 0.45 | 0.40 | 0.15 |
| 장기(`long`) | 22일 이상 | 0.55 | 0.30 | 0.15 |

- 시험일이 없으면 중기 전략을 사용하고 기본값 사용 사실을 계산 결과에 남긴다.
- 시험 임박도는 같은 상수를 점수에 더하지 않고 전략 가중치만 선택한다.
- 풀이 시간은 우선순위에 넣지 않고 리포트 참고 지표로만 사용한다.
- 추세도 점수에 넣지 않는다.

동률 정렬:

1. 추세: 악화 → 유지 → 불명 → 개선
2. 유효 표본 내림차순
3. 영역 식별자 오름차순

### 1.14 신규·표본 부족 경계

| 조건 | 계획 방식 |
|---|---|
| 완료 풀이 기록이 없음 | 첫 주 진단형 계획 |
| 기록은 있으나 신뢰 가능한 시대+주제 후보가 없음 | 시험 중요도 중심 폴백 계획 |
| 신뢰 가능한 시대+주제 후보가 있음 | 개인화 우선순위 계획 |

시험 중요도 중심 폴백에서는 취약 점수와 반복 오답을 `0`으로 두고 출제 가중치만으로 정렬한다. 이 결과는 취약 계획이 아니라 데이터 부족 폴백임을 생성 이유(`generationReason`)에 기록한다.

### 1.15 첫 주 커리큘럼

| 일차 | 필터 | 목적 |
|---|---|---|
| 1~2일차 | 시대 | 설정 우선 시대 확인 |
| 3일차 | 주제 | 주제별 기초 확인 |
| 4일차 | 유형 | 유형 후보 6종 중 하루 블록 수만큼 서로 다른 유형 확인 |
| 5일차 | 시대+주제 | 설정 우선 결합 영역 확인 |
| 6일차 | 없음 | 앞에서 적게 다룬 범위 혼합 |
| 7일차 | 진단 blueprint | 주간평가 |

- 첫 주 블록은 시대+주제+유형 3중 필터를 사용하지 않는다.
- 4일차 유형 후보 6종은 전체 강제 할당량이 아니다. 현재 question의 블록당 단일 유형 계약을 유지하기 위해 설정 순서로 순환하며, 하루 블록마다 서로 다른 유형 하나를 배정한다. 하루 블록이 2개이면 유형도 2개만 사용한다.
- 문제은행 분포 조사 전에는 일차별 비율·문항 수를 하드코딩하지 않는다.
- 7일차 평가 비율이 확정되지 않으면 기존 diagnosis 출제 로직을 명시적 폴백으로 사용한다.

### 1.16 기간과 하루 용량

```text
종료일(endDate)
= min(시작일 + 6일, 시험일 - 1일)

적용 학습시간(appliedMinutes)
= clamp(사용자 설정 시간, 1분, 300분)

하루 블록 수(dailyBlockCount)
= clamp(ceil(appliedMinutes / 30분), 1, 10)

블록별 시간(blockMinutes[index])
= min(30분, appliedMinutes - 30분 × index)
```

블록 순번(`index`)은 `0`부터 시작한다.

- 시험이 시작일로부터 7일 안에 있으면 시험 전날까지만 만들고 주간평가는 만들지 않는다.
- 시험 당일이거나 시험 전날이 시작일보다 이르면 생성할 수 있는 학습일이 없다고 안내한다.
- 신규 계획을 저장할 때 계획의 최소·최대 날짜를 시작일 열(`startDate`)과 종료일 열(`endDate`)에 함께 저장한다.
- 이월은 계획 종료일을 늘리지 않는다.
- 60분은 2블록, 300분 이상은 최대 10블록이다.
- 45분은 30분·15분 두 블록으로 나누며 블록 시간의 합이 적용 학습시간을 넘지 않게 한다.

블록 문항 수:

```text
문항 수(questionCount)
= clamp(
    floor(블록 분(blockMinutes) × 60 / 평균 풀이 초(averageSecondsPerQuestion)),
    설정 최소 문항 수,
    설정 최대 문항 수
  )
```

사용자 표본이 부족하면 버전 설정의 기본 평균 풀이 초를 사용한다. 블록당 문항 수를 상수 5개·10개로 고정하지 않는다.

초기 버전 설정값:

| 설정 | 초기값 | 근거 |
|---|---:|---|
| 기본 평균 풀이 초(`defaultAverageSecondsPerQuestion`) | 180초 | 30분 블록을 약 10문제로 시작 |
| 최소 블록 문항 수(`minimumQuestionCount`) | 1문제 | 짧은 마지막 블록 허용 |
| 최대 블록 문항 수(`maximumQuestionCount`) | 50문제 | 현재 출제 API와 과도한 단일 세션 방지 |

이 값은 코드 상수가 아니라 학습계획 설정 버전에 둔다. 실제 사용자 풀이시간과 후보 부족률을 관측해 버전을 올려 조정한다.

### 1.17 문제 후보 부족

개인화 블록의 후보는 전체 문항 수뿐 아니라 현재 question 학습계획 출제가 요구하는 점수별 문항 수까지 충족해야 한다. analytics는 같은 점수 구성 설정으로 후보 수를 검사하고, question E2E에서 두 계산의 일치를 고정한다. 총 문항은 충분하지만 특정 점수 문항이 부족한 후보도 부족 후보로 처리한다.

후보가 부족하면 다음 순서로 처리한다.

1. 다음 시대+주제 우선순위 후보로 블록을 교체한다.
2. 모든 시대+주제 후보가 부족하면 같은 시대 필터로 완화한다.
3. 완화 후에도 부족하면 해당 블록만 생략한다.
4. 실제 필터와 대체 이유를 블록 이유(`reason`)에 기록한다.
5. 일반 학습 블록이 하나도 만들어지지 않을 때만 `QUESTION_POOL_INSUFFICIENT`로 전체 생성을 중단한다.

범위를 조용히 섞거나 요청 문항 수를 채우기 위해 무관한 문제를 넣지 않는다. 첫 주 단일 축 블록은 다음 설정 후보로 바꾼 뒤, 같은 축의 상위 범위로만 완화한다.

### 1.18 계획·블록 JSON

기존 계획 요약 열(`study_plans`)은 레거시 문자열과 신규 버전 JSON을 모두 읽는다. 신규 저장 예시:

```json
{
  "schemaVersion": "2",
  "summary": "7일 학습계획",
  "configVersion": "study-plan-v2",
  "generationReason": "personalized",
  "sourceStudyPlanId": null,
  "timezone": "Asia/Seoul"
}
```

변경 번호(`revision`)와 마지막 동기화 날짜(`lastSyncedDate`)는 저장하지 않는다.
레거시 요약 문자열은 동기화·완료 때 JSON으로 강제 변환하지 않는다. 신규 계획만 버전 JSON을 쓰며 DTO가 두 형식을 같은 요약 문자열로 조립한다.

계획 항목 열(`study_plan_items`)은 기존 공용 파서와 question·diagnosis 직접 조회 경로를 유지하기 위해 **최상위 배열**로 저장한다. 필터 값도 블록 최상위에 둔다.

```json
[
  {
    "date": "2026-07-20",
    "blocks": [
      {
        "blockId": "2f4bbf18-3ba2-4d52-926f-0f67ac9bf111",
        "groupKeyId": "era=%EA%B7%BC%ED%98%84%EB%8C%80|topic=%EC%82%AC%ED%9A%8C",
        "blockType": "practice",
        "classification": "복합",
        "label": "근현대 · 사회",
        "era": "근현대",
        "topic": "사회",
        "qType": "",
        "activity": "문제 풀이",
        "questionCount": 10,
        "estimatedMinutes": 30,
        "priorityScore": 0.79,
        "reason": "취약 점수와 반복 오답 우선",
        "status": "scheduled",
        "trend": "worsening",
        "originalDate": "2026-07-20",
        "rolloverCount": 0
      }
    ]
  }
]
```

- 기존 question이 읽는 `era`, `topic`, `qType`, `classification`, `label`, `questionCount`는 최상위 필드로 유지한다.
- 기존 화면용 `isCompleted`는 저장하지 않고 analytics DTO가 `status == completed`인지로 조립한다.
- 기존 예상 시간 필드명(`estimatedMinutes`)을 유지하고 별도 `plannedMinutes`를 만들지 않는다.
- 주간평가 블록도 같은 최상위 구조를 사용하되 유형(`blockType`)은 `weekly_review`, 필터 필드는 빈 값, 문항 수는 현재 diagnosis 주간평가 문항 수와 일치시킨다.
- 신규 블록 번호(`blockId`)는 최종 저장 직전에 UUID로 한 번 발급한다.
- 신규 블록 번호는 UUID여야 한다. 레거시의 비UUID 블록 번호는 비어 있지 않고 계획 안에서 유일하면 불투명 식별자로 그대로 보존해 조회·완료·동기화를 허용한다. 누락·중복 번호만 자동 보정하지 않고 변경을 차단해 보고한다.
- 레거시 `newWeakness`, `predictionFocus`, `review`는 읽을 때 일반 학습(`practice`)으로 해석한다.
- 레거시 `weekly_review`는 주간평가로 해석한다.
- 레거시 추가 학습은 이월·완료율에서 제외하고 다음 동기화에서 취소한다.
- 레거시 완료 여부(`isCompleted=true`)는 완료 상태로 해석한다. `false`인 일반 블록은 연결된 진행 세션이 있으면 진행 중, 없으면 예정으로 해석한다.
- 완료되지 않은 레거시 주간평가가 서울 기준 과거 날짜이면 동기화에서 놓침으로 바꾼다.
- 레거시 읽기 변환은 DTO와 서비스 내부에서만 적용하고 원본 계획 번호·블록 번호·풀이 연결값은 바꾸지 않는다.
- 레거시 삭제 계획은 레거시 삭제 상태로만 읽으며 신규 삭제 기능은 제공하지 않는다.

### 1.19 상태와 완료율

계획 상태:

- 활성(`active`)
- 보관(`archived`)
- 레거시 삭제(`legacy_deleted`)

블록 상태:

- 예정(`scheduled`)
- 진행 중(`in_progress`)
- 완료(`completed`)
- 놓침(`missed`)
- 취소(`cancelled`)

허용 전이:

| 현재 | 다음 | 원인 |
|---|---|---|
| 예정 | 진행 중 | 세션 시작 |
| 예정·진행 중 | 완료 | 전체 제출 |
| 예정 | 놓침 | 주간평가 날짜 경과 |
| 예정 | 취소 | 일반 블록 이월 한도 도달 또는 레거시 추가 학습 정리 |

진행 세션 취소를 별도 블록 상태 전이로 만들지 않는다. 새 세션으로 교체되어도 블록은 다른 완료 기록이 없으면 예정 상태로 다시 계산한다.

```text
완료율(completionRate)
= 완료한 일반 학습 블록 수(completedLearningBlocks)
  / 전체 일반 학습 블록 수(totalLearningBlocks)
```

- 값은 `0~1`로 저장한다.
- 취소된 일반 블록은 분모에 남고 분자에는 들어가지 않는다.
- 주간평가와 레거시 추가 학습은 분자·분모에서 제외한다.
- 진행 중 답안 개수는 반영하지 않는다.
- 완료의 원천은 완료 세션과 풀이 기록이다. 블록 JSON 상태와 계획 테이블의 완료율 열(`completion_rate`)은 조회 성능과 레거시 호환을 위한 투영값이다.
- 블록 완료 서비스는 풀이 기록을 확인한 뒤 블록 상태와 완료율 열을 같은 계획 행 잠금 안에서 갱신한다.
- 마이페이지 GET은 풀이 기록으로 DTO 완료율을 계산하지만 저장하지 않는다. 주간 리포트도 제출 시점 풀이 기록으로 완료율 사본을 계산한다.
- 놓침·취소는 풀이 기록에 대응 세션이 없으므로 블록 JSON의 terminal 상태를 원천으로 사용한다.

### 1.20 동기화 알고리즘

마이페이지 GET은 변경하지 않는다. 화면이 GET 완료 뒤 동기화 API를 호출한다.

1. 사용자 행과 활성 계획 행을 잠근다.
2. 서울 기준 오늘과 풀이 기록으로 현재 블록 상태를 다시 계산한다.
3. 지난 주간평가가 예정이면 놓침으로 바꾼다.
4. 레거시 추가 학습 블록을 취소한다.
5. 과거 미완료 일반 블록을 우선순위 내림차순, 최초 계획일·블록 번호 오름차순으로 정렬한다.
6. 이월 횟수가 이미 2 이상이면 취소하고 다음 계획 재평가 후보로 표시한다.
7. 오늘 용량은 하루 블록 수에서 오늘 날짜에 이미 배정된 예정·진행 중·완료 일반 블록 수를 뺀 값이다. 완료 블록도 이미 소비한 학습량이므로 용량을 다시 만들지 않는다.
8. 남은 용량 안에서 오늘로 옮기고 이월 횟수를 1 증가시킨다.
9. 주간평가일에는 일반 블록을 옮기지 않는다.
10. 변경이 있을 때만 계획 JSON을 한 번 저장한다.

두 번째 요청은 과거 예정 블록이 더 없으므로 자연스럽게 `changed=false`가 된다. 별도 dedupe key, receipt, 변경 번호, 마지막 동기화 날짜가 필요하지 않다.

### 1.21 재생성과 이어풀기

계획 다시 만들기는 다음 상황에서 같은 생성 API를 사용한다.

- 밀린 학습이 3일치 이상
- 주간평가를 놓침
- 시험일 또는 학습시간 변경 반영
- 사용자의 명시적 재생성

생성 트랜잭션:

1. 사용자 행을 잠근다.
2. 활성 계획이 있으면 요청의 원본 계획 번호(`sourceStudyPlanId`)가 그 계획인지 확인한다. 활성 계획이 있는데 원본 번호가 없거나 다르면 현재 계획과 `changed=false`를 반환한다.
3. 계획 초안을 계산하고 일반 블록이 하나 이상인지 검증한다.
4. 기존 활성 계획을 보관하고 신규 계획을 저장한다.
5. 활성 계획 고유 인덱스로 중복 생성을 최종 차단한다.

오래된 중복 요청이면 새 계획을 만들지 않고 현재 활성 계획과 `changed=false`를 반환한다.

진행 중 세션이 있어도 재생성을 허용한다. 화면에는 “이어푼 결과는 이전 계획에 반영되며 새 계획 완료율에는 포함되지 않습니다”라고 안내한다.

새 세션 시작은 활성 계획의 서울 기준 오늘 블록만 허용한다. 이미 시작된 세션의 이어풀기와 제출은 원본 계획이 보관되어도 허용한다.

완료 서비스는 전달받은 계획 번호와 블록 번호로 계획 행 하나만 잠근다. 활성·보관 계획을 모두 허용하고, 해당 계획·블록에 연결된 완료 세션과 풀이 기록을 조회한다. 완료 세션이 없거나 기록 수가 세션 전체 문항 수와 다르면 변경하지 않는다. 유효한 완료 세션이 여러 개이면 자동 선택하지 않고 데이터 무결성 오류로 기록한다. 유효한 세션 하나를 원본 세션으로 확정한 뒤 같은 세션의 완료 효과를 한 번만 반영한다.

## 2. AI 주간리포트

### 2.1 결정 결과와 AI 역할

결정 코드가 만드는 값:

- 평가 점수·정답 수·전체 문항 수
- 이전 평가와의 점수 변화
- 계획 완료율
- 좋아진 영역
- 우선 보완 영역
- 유형별 풀이시간 요약
- 다음 계획 대상

AI 작성 에이전트가 만드는 값:

- 코멘트 1개
- 설정 최대 개수 안의 학습 팁

AI 검증 에이전트는 작성 문장이 제공된 근거에서 벗어나지 않았는지 판정한다. 어떤 AI도 숫자·취약 판정·계획 대상을 만들거나 변경하지 않는다.

결정 결과 선정 규칙:

| 결과 | 선정 조건 | 정렬 | 최대 개수 |
|---|---|---|---:|
| 좋아진 영역(`strengths`) | 추세가 개선이고 두 추세 구간 모두 최소 표본 충족 | 추세 차이 오름차순, 유효 표본 내림차순 | 3 |
| 우선 보완 영역(`priorityImprovements`) | 현재 상태가 취약 | 취약 점수, 반복 오답, 유효 표본 내림차순 | 3 |
| 풀이시간 요약(`timeSummary`) | 유형별 사용자 중앙 풀이시간 표본 5개 이상이며 기준 대비 1.3배 이상 | 시간 비율 내림차순 | 2 |
| 다음 계획 대상(`nextPlanTargets`) | 1.13의 계획 후보 | 계획 우선순위 내림차순 | 3 |

좋아진 영역·우선 보완 영역·다음 계획 대상의 분석 단위는 시대+주제로 통일한다. 유형은 풀이시간 요약에 사용하고, 3중 조합은 취약점 상세 화면의 근거 탐색용으로만 유지한다.

```text
유형별 시간 비율(timeRatio)
= 사용자 유형별 중앙 풀이 초(userMedianSeconds)
  / 같은 계획 기간 사용자 전체 문항 중앙 풀이 초(referenceMedianSeconds)
```

- 풀이시간이 `NULL`, `0`, 음수인 기록은 시간 계산에서 제외한다.
- 기준 중앙값은 같은 사용자의 원본 계획 기간 완료 기록으로 계산해 다른 사용자 전체 기록 조회를 만들지 않는다.
- 유형 표본은 5개, 기준 전체 표본은 10개 이상일 때만 시간 요약을 만든다.
- 좋아진 영역이 없으면 억지로 안정 영역을 대신 넣지 않고 빈 배열로 둔다.
- 취약 영역이 없으면 표본 부족을 취약으로 승격하지 않고 빈 배열로 둔다.
- 다음 계획 대상은 보완 영역과 같을 필요가 없다. 시험 중요도와 반복 오답까지 포함한 계획 우선순위를 사용한다.
- 리포트 유형(`reportType`)은 원본 계획 생성 이유가 첫 주 진단형이거나 이전 완료 주간평가가 없으면 `first_week`, 그 외에는 `weekly`다. 생성 이유가 없는 레거시 계획도 이전 주간평가 유무로 결정한다.
- 개수·최소 표본·시간 비율 임계값은 리포트 설정 버전에 두며 AI가 바꾸지 않는다.
- 학습 팁 최대 개수(`maximumTipCount`)의 초기값은 3개다.

### 2.2 수집 기준

- 주간평가 제출 완료 트랜잭션에서 계획 행을 잠근다.
- 세션·계획·블록 연결과 전체 제출을 확인한다.
- 같은 평가 세션이 이미 등록되어 있으면 기존 JSON을 반환한다.
- 점수·비교·완료율·분석을 계산해 결과(`result`)로 고정한다.
- 제출 트랜잭션이 길어지는지 응답 시간을 관측한다. 기준 초과가 확인되면 분석만 worker로 옮기는 변경을 별도 검토한다.

비교 대상 우선순위:

1. 이전에 완료된 최신 주간평가
2. 최신 일반 진단평가
3. 둘 다 없으면 비교 기준 부족(`INSUFFICIENT_BASELINE`)

리포트 생성 중 새 풀이가 추가되어도 고정 결과를 다시 계산하지 않는다. 누락 복구 시 정확한 제출 시점을 알 수 없으면 복구 시각을 사용하고 복구 사본 여부(`recoveredSnapshot=true`)를 남긴다.

### 2.3 저장 JSON

주간평가를 제출하지 않은 계획의 주간 리포트 데이터(`weekly_report_data`)는 SQL `NULL`이다. 제출 뒤에는 최상위 JSON 객체만 저장한다.

```json
{
  "schemaVersion": "1",
  "status": "pending",
  "reportType": "first_week",
  "sourceSessionId": 123,
  "result": {
    "snapshotAt": "2026-07-19T12:00:00Z",
    "recoveredSnapshot": false,
    "assessment": {
      "score": 82,
      "totalScore": 100,
      "correctCount": 41,
      "totalCount": 50
    },
    "comparison": {
      "status": "AVAILABLE",
      "baselineType": "weekly_review",
      "baselineSessionId": 98,
      "previousScore": 76,
      "scoreChange": 6
    },
    "planProgress": {
      "completedLearningBlocks": 10,
      "totalLearningBlocks": 12,
      "completionRate": 0.833
    },
    "strengths": [],
    "priorityImprovements": [],
    "timeSummary": [],
    "nextPlanTargets": []
  },
  "content": {
    "comment": null,
    "tips": [],
    "fallbackUsed": false,
    "validation": null
  },
  "worker": {
    "attemptCount": 0,
    "availableAt": "2026-07-19T12:00:00Z",
    "startedAt": null,
    "lastError": null
  },
  "nextPlan": {
    "status": "pending",
    "studyPlanId": null,
    "blockedReason": null
  },
  "version": "weekly-report-v1",
  "model": "configured-model",
  "createdAt": "2026-07-19T12:00:00Z",
  "readyAt": null
}
```

준비 완료일 때 최종 문장(`content`) 예시:

```json
{
  "comment": {
    "text": "이번 주에는 조선 정치 영역이 좋아졌어요.",
    "evidenceIds": ["strength-1"]
  },
  "tips": [
    {
      "text": "근현대 사회 문제를 짧게 나누어 풀어 보세요.",
      "evidenceIds": ["priority-1"]
    }
  ],
  "fallbackUsed": false,
  "validation": {
    "guard": "passed",
    "validator": "passed"
  }
}
```

계산 결과(`result`)의 각 영역 항목에는 영역 식별자, 표시 이름, 근거 번호, 표본 수와 필요한 계산값을 넣는다. 전체 풀이 이력이나 원본 답안은 넣지 않는다.

화면용 제목·점수 요약·완료율 문구는 저장하지 않는다. 조회 시 리포트 버전(`version`)에 맞는 출력기가 `result`와 `content`로 DTO를 조립하고 HTML escaping을 적용한다.

JSON 주의사항:

- 최상위는 Python 사전(`dict`) 또는 `None`만 허용한다.
- `None`은 SQL `NULL`로 저장한다. JSON `null`, 배열, 문자열, 숫자, 불리언은 DB 제약으로도 거부한다.
- 완료율은 `0~1` 범위다.
- 시각은 UTC ISO 8601, 계획 날짜 판단은 `Asia/Seoul`을 사용한다.
- 원본 프롬프트·API 키·개인정보·외부 오류 원문을 저장하지 않는다.
- 오류는 허용된 코드와 안전한 메시지만 저장한다.
- 계획 행을 잠근 뒤 주간 리포트 열만 갱신한다. 오래 읽은 다른 계획 JSON을 함께 덮어쓰지 않는다.

### 2.4 상태와 작업 처리

리포트 상태:

- 대기(`pending`)
- 실행 중(`running`)
- 준비 완료(`ready`)
- 실패(`failed`)

자동 재시도는 재시도 상태를 따로 만들지 않는다. 실행 가능 시각(`availableAt`)을 미래로 바꾸고 상태를 다시 `pending`으로 둔다. 시도 횟수(`attemptCount`)와 마지막 오류(`lastError`)로 최초 대기와 재시도를 구분한다.

다음 계획 상태:

- 대기(`pending`)
- 진행 세션으로 보류(`blocked`)
- 성공(`succeeded`)
- 실패(`failed`)

작업 처리기 규칙:

1. Compose에서 동일 이미지의 `run_ai_worker` 프로세스 하나만 실행한다.
2. PostgreSQL 자문 잠금을 얻은 프로세스만 처리한다.
3. 리포트 생성 후보는 실행 가능 시각이 지난 `pending` 또는 정지 기준을 넘긴 `running`이다.
4. 리포트 생성 후보는 계획 행을 잠그고 상태·시도 횟수를 재확인한 뒤 `running`으로 claim한다.
5. 완료 저장 때 같은 시도 횟수인지 다시 확인해 늦은 결과를 차단한다.
6. 정지 작업은 다시 `pending`으로 돌리되 최대 시도 횟수를 넘으면 `failed`로 닫는다.
7. 다음 계획 복구 후보는 리포트가 `ready`이고 다음 계획이 `pending`이며 실행 가능 시각이 지난 행이다. 이 분기는 리포트 상태와 AI 문장을 바꾸지 않고 다음 계획만 처리한다.
8. 다음 계획의 일시적 인프라 오류는 다음 계획을 `pending`으로 유지하고 worker 실행 가능 시각을 뒤로 미룬다. 후보 부족 같은 영구 오류만 `failed`로 저장한다.
9. 완료된 주간평가 세션과 계획·블록 연결이 있지만 리포트 JSON이 SQL `NULL`인 행을 주기적으로 조회해 `recoveredSnapshot=true`인 `pending` JSON을 등록한다.

단일 worker이므로 lease token과 heartbeat는 사용하지 않는다. LLM 호출마다 60초 제한을 적용하고 작업 처리 5분 초과를 정지 기준으로 사용한다. 최대 작업 시도는 3회이며 인프라 오류는 30초, 120초 뒤 다시 시도한다. 이 값은 worker 설정 버전에 둔다. 여러 worker가 필요해지면 JSON 열 기반 작업 큐를 확장하지 않고 별도 작업 테이블을 다시 설계한다.

### 2.5 AI 작성·검증

작성 AI 입력:

- 리포트 유형
- 저장된 계산 결과(`result`)
- 허용 근거 번호
- 표현 정책과 금지 표현

작성 AI 출력은 구조화 JSON으로 받는다. 코드 검증 항목:

- 코멘트·팁 필드와 길이
- 입력에 존재하는 근거 번호만 사용
- 입력에 없는 숫자·원인 추측 금지
- 표본 부족을 확정 취약으로 표현하지 않음
- 비난·낙인·합격 보장 표현 금지

코드 검증을 통과한 결과만 검증 AI에 보낸다. 검증 AI는 근거 이탈, 과장, 어조, 실행 가능성을 판정한다.

```text
작성 AI 1회
→ 코드 검증
→ 검증 AI 1회
→ 성공이면 AI 문장
→ 어느 단계든 실패하면 기본 문장
```

재작성은 하지 않는다. AI 호출은 리포트당 최대 두 번이다. AI 호출 실패는 리포트 실패가 아니라 기본 문장 사용(`fallbackUsed=true`)으로 처리하고 상태를 `ready`로 만든다.

### 2.6 다음 계획

리포트가 `ready`가 된 뒤 같은 worker가 다음 계획을 처리한다. 중간에 프로세스가 종료되어도 2.4의 `ready + nextPlan.pending` 복구 경로가 다시 처리한다.

1. 원본 계획 행을 잠근다.
2. 이미 생성된 다음 계획 번호가 있으면 종료한다.
3. 진행 중인 일반 문제풀이 또는 진단평가 세션이 있으면 `blocked`로 저장한다.
4. 없으면 원본 계획을 보관하고 다음 계획을 생성해 `succeeded`로 저장한다.

원본 계획이 이미 보관되어 있고 다른 활성 계획이 존재하면 새 계획을 만들지 않는다. 사용자가 먼저 만든 활성 계획을 다음 계획으로 인정하고 그 계획 번호를 저장한 뒤 `succeeded`로 종료한다.

마이페이지 동기화는 다음 계획이 `pending` 또는 `blocked`이면 진행 세션을 다시 확인하고, 없으면 같은 생성 서비스를 호출한다. 별도 다음 계획 버튼은 만들지 않는다.

다음 계획은 리포트의 다음 계획 대상(`nextPlanTargets`)을 우선 사용하되, 현재 시험일·학습시간과 최신 문제은행 후보를 다시 확인한다. 이미 생성된 계획 번호와 활성 계획 고유 인덱스로 중복 생성을 막는다.

## 3. API·트랜잭션·협조

### 3.1 모듈 구조

```text
app/analytics/service/
  weakness.py       # Wilson 취약 점수·상태·추세·분석 행
  taxonomy.py       # 분류 정규화·영역 식별자·표시명
  study_plan/
    config.py       # 버전 설정
    planner.py      # 취약 분석 결과를 소비하는 순수 계획 계산
    service.py      # 생성·동기화·완료·시작 검증 트랜잭션
    dto.py          # 마이페이지 응답
  weekly_report/
    config.py       # 버전 설정
    service.py      # 수집·분석·렌더링·다음 계획 연결
    llm.py          # 작성·검증 AI와 코드 검증
    worker.py       # claim·재시도·정지 복구
app/analytics/management/commands/
  run_ai_worker.py
```

작은 헬퍼 파일을 늘리지 않고 기능 단위로 묶는다. 기존 `studyplan.py`는 외부 import가 남아 있는 동안 새 서비스로 위임하는 호환 창구로 유지한다.

### 3.2 API 계약

```text
GET  /analytics/mypage/
GET  /analytics/mypage/?format=json
POST /analytics/study-plan/create/
POST /analytics/study-plan/sync/
POST /analytics/study-plan/report/retry/
```

- 형식 지정이 없는 마이페이지 GET은 기존 HTML을 렌더링한다.
- `format=json`은 같은 조회 서비스의 JSON DTO를 반환하며 데이터를 변경하지 않는다.
- 리포트 카드는 이 JSON 응답만 폴링한다. 별도 리포트 상태 주소는 만들지 않는다.

생성 요청:

```json
{
  "reason": "settings_changed",
  "sourceStudyPlanId": 42
}
```

동기화 요청:

```json
{
  "studyPlanId": 42
}
```

리포트 재시도 요청:

```json
{
  "studyPlanId": 42
}
```

생성·동기화·재시도 공통 응답:

```json
{
  "ok": true,
  "changed": false,
  "studyPlan": {
    "studyPlanId": 42,
    "status": "active",
    "planVersion": 3,
    "summary": "7일 학습계획",
    "startDate": "2026-07-20",
    "endDate": "2026-07-26",
    "completionRate": 0.833,
    "plans": []
  },
  "weeklyReport": {
    "status": "ready",
    "reportType": "weekly",
    "result": {},
    "content": {},
    "nextPlan": {
      "status": "succeeded",
      "studyPlanId": 43,
      "blockedReason": null
    }
  }
}
```

- 마이페이지 JSON 응답도 같은 `studyPlan`, `weeklyReport` 구조를 사용하고 조회 응답에는 `changed`를 넣지 않는다.
- 활성 계획이 없으면 `studyPlan`은 `null`, 주간평가 제출 전이면 `weeklyReport`는 `null`이다.
- 계획 목록(`studyPlan.plans`)은 기존 최상위 배열 구조다.
- 블록 DTO는 저장 필드를 유지하면서 완료 여부(`isCompleted`)와 시작 가능 여부(`canStart`)를 analytics가 계산해 추가한다.
- 계획 생성 순번(`planVersion`)은 유지하지만 상태 충돌 번호로 사용하지 않는다.

변경 번호(`revision`)와 기대 변경 번호(`expectedRevision`)는 받지 않는다. 사용자 블록 편집 기능이 없고, 모든 변경은 서버 규칙과 행 잠금 안에서 직렬화되기 때문이다.

### 3.3 잠금 순서

| 경로 | 잠금 |
|---|---|
| 계획 생성·재생성 | 사용자 → 현재 활성 계획 |
| 동기화 | 사용자 → 활성 계획 |
| 새 문제 세션 시작 | question·diagnosis 사용자 잠금 → analytics 검증은 읽기 |
| 제출 중 블록 완료 | question·diagnosis 세션 잠금 → 전달된 계획 행만 잠금 |
| 리포트 claim·완료 | 자문 잠금 → 계획 행 |

블록 완료 경로는 사용자 행을 잠그지 않는다. 제출 경로가 이미 세션을 잠근 뒤 analytics를 호출하므로 세션 → 사용자 역순 잠금으로 생길 수 있는 교착을 피한다.

### 3.4 오류 계약

| 상황 | 응답 |
|---|---|
| 인증 실패 | `401` 또는 `403` |
| 계획·블록 없음 또는 다른 사용자 | `404` |
| 입력 형식 오류 | `400` |
| 오늘이 아닌 블록 새 시작 | `409 BLOCK_NOT_DUE` |
| 실행 경로 불일치 | `409 BLOCK_ROUTE_MISMATCH` |
| 완료·놓침·취소 블록 새 시작 | `409 BLOCK_TERMINAL` |
| 일반 학습 블록 후보가 모두 부족 | `422 QUESTION_POOL_INSUFFICIENT` |
| 평가 출제 기준 부족 | `422 ASSESSMENT_BLUEPRINT_UNAVAILABLE` |
| 제출 답안 미완료 | `422 SESSION_INCOMPLETE` |
| 리포트·세션·계획 연결 불일치 | `500 DATA_INTEGRITY_ERROR` |

원본 계획이 이미 바뀐 재생성·동기화 중복 요청은 충돌 오류 대신 현재 활성 계획과 `changed=false`를 반환한다.

### 3.5 외부 협조

question 담당:

- 새 일반 문제풀이 세션 교체 트랜잭션에서 사용자 행 잠금
- 새 계획 세션 시작 전 analytics 시작 검증 호출
- 보관 계획에 연결된 기존 세션 제출도 analytics 완료 함수 호출
- 신규 세션 학습일을 `Asia/Seoul` 달력 날짜로 기록

diagnosis 담당:

- 진행 중 목록 GET의 삭제 부작용 제거
- 같은 평가 유형의 세션 교체를 사용자 잠금이 포함된 한 트랜잭션으로 처리
- 제출 트랜잭션에서 세션과 풀이 기록을 잠그고 제출 문항 번호가 세션 전체 문항 번호와 정확히 일치하는지 검증
- 새 주간평가 시작 전 analytics 시작 검증 호출
- 보관 계획에 연결된 기존 주간평가 제출도 analytics 완료 함수 호출
- 신규 세션 학습일을 `Asia/Seoul` 달력 날짜로 기록

상세 내용은 [question·diagnosis 연동 협조 요청서](./question_diagnosis_연동_협조_요청서.md)를 따른다.

### 3.6 DB 요청

- 계획 테이블(`study_plan_mypage`)에 주간 리포트 데이터(`weekly_report_data JSONB NULL`) 열 하나 추가
- SQL `NULL` 또는 최상위 JSON 객체만 허용하는 CHECK 추가
- `init.sql`, `alter_apply_latest.sql`, `managed=False` Django 모델에 같이 반영
- 기본값·백필·신규 테이블·초기 JSON 인덱스는 추가하지 않음

상세 SQL은 [DB 주간리포트 JSONB 열 추가 요청서](./DB_주간리포트_JSONB_컬럼_추가_요청서.md)를 따른다.

## 4. 구현·전환 순서

shadow·canary 없이 직접 전환한다. 기존 계획 데이터를 다른 테이블로 옮기지 않고 nullable 열 하나만 추가한다.

### 1단계 — 조사·DB

- 문제은행 시대·주제·유형 분포 조사
- 첫 주 일차별 비율과 문항 수 설정 초안 승인
- 계획 테이블 백업과 복원 절차 확인
- 기존 활성 계획의 JSON 최상위 배열 여부, 날짜 오류, 블록 번호 누락·중복 현황을 읽기 전용으로 조사하고 자동 수정하지 않음
- JSONB 열·CHECK·Django 모델 적용

통과 조건: SQL 재실행 성공, 기존 행 수·계획 번호·계획 JSON 변화 0건, JSON 객체 제약 확인.

### 2단계 — 계획

- Wilson 분석과 계획용 시대+주제 집계
- 버전 설정과 순수 계획 계산기
- 레거시 JSON 읽기와 신규 JSON 쓰기
- 읽기 전용 마이페이지와 풀이 기록 기반 완료율
- 생성·동기화·재생성 트랜잭션

통과 조건: 결정론, 하루 용량, 후보 폴백, 활성 계획 한 개, 동기화 멱등 검증.

### 3단계 — question·diagnosis 연동

- 시작 검증
- 보관 계획 이어풀기·완료
- 주간평가 제출 시 리포트 대기 등록
- 서울 기준 날짜 통일

통과 조건: 시작·이어풀기·제출 E2E와 중복 효과 1회.

### 4단계 — 리포트

- 단일 worker claim·자동 재시도·정지 복구
- AI 없이 기본 문장 리포트 E2E
- 작성 AI·코드 검증·검증 AI 연결
- 다음 계획 자동 생성·보류·재확인

통과 조건: AI 실패에도 `ready`, 중복 리포트·계획 없음, 정지 작업 복구.

### 5단계 — 화면·전환

- 마이페이지 리포트 카드와 상태 조회
- 밀림·평가 놓침·진행 세션 재생성 안내
- 전환 당시 활성 레거시 계획 E2E
- 미사용 analytics 주소 정리

통과 조건: 기존 화면 회귀 없음, 레거시 계획에서도 주간평가 → 리포트 → 다음 계획 정상.

## 5. 롤백과 운영

- 적용 전 `study_plan_mypage` 백업을 남긴다.
- 계획 기능 문제는 analytics view를 기존 `studyplan.py` 호환 경로로 되돌린다.
- 새 방식으로 생성된 계획 수와 JSON 형식을 확인한 뒤 롤백한다.
- 리포트 문제는 feature flag를 끄고 worker를 중지한다. 계획·평가 제출은 유지한다.
- JSONB 열은 즉시 삭제하지 않고 SQL `NULL` 또는 기존 값을 유지한다.
- 기존 계획 번호·블록 번호·풀이 연결값을 수정하거나 삭제하지 않는다.
- 단일 worker는 동일 이미지의 별도 Compose 서비스로 실행한다.
- 작업 수, 처리시간, fallback 비율, 실패 수, JSON 크기와 테이블 팽창을 관찰한다.

## 6. 필수 검증 시나리오

### 6.1 취약점

- 1문제 1오답은 표본 부족, 충분한 표본의 높은 오답률은 취약으로 구분
- Wilson 계수 `1.28`, 최소 표본 `3.0`, 취약 `0.50`, 안정 `0.20` 경계
- 오늘·14일·28일 기록 가중치 `1·0.5·0.25`
- 추세 `±0.10` 경계와 점수 미가산 확인
- 두 14일 추세 구간은 감쇠 없이 구간 내 균등 가중치로 Wilson 점수를 비교함
- 입력 순서가 달라도 같은 점수·판정·정렬
- 취약점 화면은 상세 조합을 표시하되 계획 후보는 시대+주제와 시대만 사용
- 마이페이지는 취약 상태만 취약 점수순으로 표시하고 점수·오답률 백분율을 노출하지 않음
- 마이페이지 막대 길이가 취약 점수 정렬과 단조 일치하고 표본 부족 빈 상태 문구가 표시됨
- 오답률 상세의 숫자·정렬은 선택 기간 raw 기준이고 취약 배지만 90일 감쇠 기준임
- 최근 7일 raw 목록에 없는 항목을 오답률 상세에 추가하지 않음
- 세션·기간 모달은 raw 기록을 유지하고 `취약 TOP` 대신 `오답 TOP`을 사용함
- 도넛의 기타 묶음에 단일 취약 배지를 붙이지 않음
- 현재 판정 경로는 SolveRecords, 원시 기록 경로는 snapshot 또는 범위 재집계를 사용하며 값이 섞이지 않음
- 영역 식별자의 필드 순서와 percent-encoding 왕복, 특수문자 충돌 없음
- 분류 표시명이 같아도 영역 식별자가 다르면 별도 항목으로 유지됨
- 같은 요청 안에서 90일 기록 조회와 분석 결과를 재사용함
- 실제 데이터 캘리브레이션에서 상태 분포·상위 목록·추세 안정성과 화면 응답 시간을 기록함

### 6.2 계획

- 같은 입력·설정이면 UUID와 생성 시각을 제외한 계획 초안 동일
- 완료 기록 없음은 첫 주, 기록은 있으나 신뢰 후보 없음은 시험 중요도 폴백
- 첫 주 1~2일 시대, 3일 주제, 4일 유형 6종, 5일 시대+주제, 6일 혼합, 7일 평가
- 첫 주에 3중 필터 없음
- 시험 없음, 당일, `+1일`, `+7일`, `+8일` 경계
- 60분 2블록, 300분 10블록, 300분 초과 상한
- 블록 최대 30분과 설정 기반 문항 수
- 후보 부족 시 다음 시대+주제 → 시대 완화 → 블록 생략
- 전체 후보 수는 충분하지만 question 기본 점수 구성의 특정 점수 문항이 부족하면 같은 부족 폴백이 실행됨
- analytics 후보 검증과 실제 question 학습계획 시작의 점수별 요구 문항 수가 일치함
- 일부 블록 생략에도 계획 생성, 모든 일반 블록 부족일 때만 전체 실패
- 대체 범위와 이유 기록
- 독립 복습·삭제·이동·교체·추가 학습 없음
- 동시 생성에도 활성 계획 한 개
- 신규 저장 시 시작일·종료일 열 동시 갱신
- 비어 있지 않고 계획 안에서 유일한 레거시 비UUID 블록 번호는 그대로 조회·완료·동기화됨
- 누락·중복 레거시 블록 번호는 자동 발급하지 않고 변경을 차단함

### 6.3 진행·이월·이어풀기

- GET만으로 계획·세션·답안 변화 0건
- 동기화 반복 시 두 번째 요청 `changed=false`
- 우선순위 내림차순, 동률 최초 계획일·블록 번호 순으로 오늘 용량 안에 이월
- 이월 0→1, 1→2 허용, 이미 2회면 세 번째 이월 없이 취소
- 레거시 추가 학습 취소와 완료율 분자·분모 제외
- 취소된 일반 블록은 완료율 분모 유지
- 주간평가 날짜 경과 시 놓침, 이월 없음
- 전체 제출 전 미완료, 전체 제출 후 한 번만 완료
- diagnosis가 중복·누락 문항 목록을 제출하면 세션·블록·리포트가 완료되지 않음
- diagnosis 동시 제출에서도 세션 완료·블록 완료·리포트 등록 효과가 한 번만 발생함
- 예정일이 아니거나 종료된 블록 새 시작 차단
- 재생성 뒤 보관 계획 세션 이어풀기·제출은 원본 계획에만 반영
- 진행 세션이 있는 재생성 허용과 안내 문구
- 풀이 유형별 진행 세션 최대 한 개

### 6.4 리포트

- 주간평가 중복 제출에도 같은 계획의 리포트 JSON 하나
- 완료율 `0.833` 저장과 화면 `83.3%` 표시
- 비교 평가 없음은 `INSUFFICIENT_BASELINE`과 변화량 `null`
- 작성 AI 최대 1회, 검증 AI 최대 1회, 재작성 없음
- 좋아진 영역·보완 영역·시간 요약·다음 계획 대상이 2.1의 조건·정렬·최대 개수와 일치함
- 원본 계획 생성 이유가 없더라도 이전 주간평가가 없으면 `first_week`, 있으면 `weekly`임
- 작성·코드 검증·검증 AI 각각의 실패가 기본 문장 `ready`로 종료
- `pending → running → ready`, 자동 재시도는 `pending + availableAt`
- 정지 `running` 회수와 최대 시도 초과 `failed`
- 화면 DTO를 조회 시 생성하고 `renderedReport` 미저장
- `ready + nextPlan.pending` 복구는 AI를 다시 호출하지 않고 다음 계획 단계만 실행
- 리포트 JSON 누락 복구는 완료 주간평가 연결을 찾아 `recoveredSnapshot=true`로 한 번만 등록
- 진행 세션 없음은 다음 계획 자동 생성, 있음은 보류, 마이페이지 진입 뒤 재확인
- 다음 계획 중복 생성 없음
- HTML 마이페이지 GET과 `?format=json` 조회 모두 읽기 전용이며 JSON 응답 계약이 동일함
- 전환 당시 활성인 레거시 JSON 계획에서 주간평가 제출 → 리포트 → 기존 계획 보관 → 다음 계획 생성

### 6.5 DB·보안

- JSONB 열 nullable, 기존 행 SQL `NULL`
- 객체는 허용하고 배열·문자열·숫자·불리언·JSON `null` 거부
- 변경 SQL 두 번 실행 가능
- 제약 교체 실패 시 기존 제약 삭제도 같은 `DO` 블록에서 롤백
- DB 변경 전후 기존 행 수·계획 번호·블록 번호·풀이 연결값 변화 0건
- 원본 답안·전체 프롬프트·API 키·개인정보·외부 오류 원문 미저장
- 다른 사용자 계획·리포트 접근 차단
- 렌더링 문자열 escaping
