# 주간평가 식별·리포트 연동 — 협조 요청서 (diagnosis / question 앱)

`docs/mypage/weekly_review_ai_report_plan.md`(주간 AI 리포트)와
`docs/mypage/study_plan_policy.md`(이월·미응시·상태 분기)의 구현이
analytics 앱 밖의 변경을 필요로 한다. 범위 밖 4건을 아래와 같이 담당자 반영을 요청한다.

**전제**: `solve_sessions.review_type` 컬럼의 DB 반영은 DB 담당자에게 별도 요청이
진행 중이다. 요청 1~2는 그 적용 이후에만 배포할 수 있다. DB 요청 내용 요약:

- `init.sql`: `solve_sessions` CREATE TABLE 안에 `review_type VARCHAR(20) NULL` 컬럼 직접 추가
- `alter_apply_latest.sql`: `ADD COLUMN IF NOT EXISTS review_type VARCHAR(20) NULL`
- 허용값 CHECK 제약: `review_type IS NULL OR review_type IN ('weekly_review')`
- 주간평가 조회용 partial index (`weekly_review_ai_report_plan.md`의 "solve_sessions 변경" 참조)
- `study_plan_mypage` active 유일성 partial unique index (`study_plan_policy.md` 참조)

## 현재 구현 상태 (이미 반영된 것 — 재작업 불필요)

혼선 방지를 위해 diagnosis 앱에 이미 구현돼 있는 부분을 먼저 명시한다.

- `DiagnosisStartRequestSerializer`에 `studyplan_id`, `study_plan_block_id` 필드 존재
- `diagnosis_start`의 주간평가 블록 검증 (`_find_weekly_review_block` — active 계획 조회,
  blockId 매칭, `weekly_review` 타입 확인)
- 세션 시작 시 `SolveRecords`에 `studyplan_id`, `study_plan_block_id` 저장
- 제출 완료 시 블록 완료 처리 (`_complete_weekly_review_block_for_session` →
  `complete_study_plan_block_by_id`)

즉 "record 연결값" 경로는 완성돼 있고, 빠져 있는 것은 **세션 단위 식별자(`review_type`)와
리포트 작업 enqueue, 출제 방식**이다.

---

## 요청 1. `SolveSessions.review_type` 모델 컬럼 선언 (question 앱)

### 배경

주간평가는 진단평가 API로 실행되므로 세션 데이터만으로는 일반 진단평가와 구분되지 않는다
(`session_type='diagnostic'`, `status='completed'` 동일). 현재는 record의
`studyplan_id`/`study_plan_block_id` 존재 여부로 간접 추정하는데, 최신 설계는
`SolveSessions.review_type='weekly_review'`를 1차 식별 기준으로 확정했다
(`weekly_review_ai_report_plan.md`). 이 식별자가 있어야 analytics가
주간평가 완료/미응시 분기, 리포트 비교 대상 선택, 오늘 계획 공백 복구를 구현할 수 있다.

### 요청 내용

`app/question/models.py`의 `SolveSessions`에 컬럼을 선언한다
(모델이 `managed=False`이므로 DB ALTER와 별개로 모델 선언이 있어야 ORM이 읽는다).

```python
review_type = models.CharField(max_length=20, blank=True, null=True)
```

- 값: `NULL`(일반 세션) | `'weekly_review'`(주간평가). 다른 값은 현재 없다.
- 기존 데이터는 NULL 유지. 과거 주간평가는 record 연결값 fallback으로 식별한다
  (analytics 측에서 처리, 아래 "제공 사항" 참조).

## 요청 2. 주간평가 세션에 `review_type` 저장 (diagnosis 앱)

### 요청 내용

1. `diagnosis_start`에서 주간평가 블록 검증(`weekly_review_block`)을 통과한 요청은
   세션 생성 시 `review_type='weekly_review'`를 저장한다.

```python
session = SolveSessions.objects.create(
    ...,
    review_type="weekly_review" if weekly_review_block else None,
)
```

2. 일반 진단평가 세션은 `review_type=None`으로 저장한다 (기본값이므로 변경 없음).
3. record의 `studyplan_id`/`study_plan_block_id` 저장은 현행 유지 —
   블록 연결·진행률 계산의 보조 기준으로 계속 쓴다.

### 함께 확인 필요: 시작 시 진행 중 세션 삭제 범위

현재 `diagnosis_start`는 시작 전에 사용자의 `session_type='diagnostic'` +
`in_progress` 세션을 **일괄 삭제**한다 (diagnosis/views.py 197행 부근).
주간평가도 diagnostic이므로 이대로면:

- 일반 진단평가를 시작하면 **진행 중이던 주간평가 세션이 삭제**된다 (역방향도 동일).

`review_type` 도입 후 삭제 범위를 같은 `review_type`끼리로 한정할지 정책 확인을 요청한다.
권장: `.filter(review_type=...)` 조건을 추가해 일반↔주간평가가 서로의 진행 세션을
지우지 않게 한다.

## 요청 3. 제출 완료 시 주간 리포트 작업 enqueue (diagnosis 앱)

### 배경

주간평가 제출이 AI 리포트 생성의 트리거다. 제출 API는 리포트를 직접 만들지 않고
작업 row만 등록하며, 생성은 analytics 백그라운드 worker가 담당한다.

### 요청 내용

`diagnosis_submit` 완료 처리에 다음을 추가한다.

1. enqueue 조건: 해당 세션이 `review_type='weekly_review'`이고 `status='completed'`.
2. analytics가 제공하는 enqueue 서비스 함수를 **제출 트랜잭션 안에서** 호출한다.
   함수 내부가 `(user_id, session_id)` 기준 upsert(`ON CONFLICT DO NOTHING`)라
   중복 제출·재시도에 멱등하다.
3. record 연결값(`studyplan_id`)이 있으면 `source_studyplan_id`로 전달하고,
   없으면 NULL로 enqueue는 유지한다 (블록 완료 처리만 건너뜀 — 현행 로직과 동일).
4. worker 알림은 함수 내부에서 `transaction.on_commit()`으로 등록된다.
   제출 API는 호출만 하면 되고, 커밋 전 알림·직접 실행을 추가하지 않는다.

### 금지 사항 (설계 확정)

- 제출 API는 Collector/Analyst/Recommender/Writer/Planner를 **직접 실행하지 않는다**.
- 제출 API는 기존 active 학습계획을 **archived 처리하지 않는다**
  (리포트 `READY` 이후 analytics worker가 Planner를 자동 실행하고 finalize 트랜잭션에서 교체).
- 이미 `READY`/`RUNNING`인 리포트 row를 `PENDING`으로 되돌리지 않는다 (함수 내부 보장).

### 시점 의존성

`weekly_ai_reports` 테이블과 enqueue 함수는 analytics 구현 범위다.
analytics가 함수를 제공하기 전에는 이 요청을 반영할 수 없으므로,
요청 1~2를 먼저 반영하고 요청 3은 analytics 측 준비 완료 통보 후 반영한다.

## 요청 4. 주간평가 출제를 고정 비율 종합평가로 변경 (diagnosis 앱)

### 배경

현재 `_pick_diagnosis_question_ids()`는 전체 문제에서 50문항/100점 조합을
완전 무작위로 뽑는다. 주간평가의 목적은 진단평가·지난 주간평가 대비
**시점 간 정답률 비교**인데, 매회 문항 분포(시대·주제·유형·난이도)가 다르면
점수 변화가 실력 변화인지 출제 분포 차이인지 구분할 수 없다.

취약점 기반 출제로 바꾸는 것이 아니다 — 취약 문제만 내면 분포가 더 왜곡된다.
취약 판정은 평가 **후** 분석·다음 계획 생성에 쓰이고(설계 확정), 출제는 분포가
고정된 종합평가여야 한다 (`study_plan_policy.md` "출제 방식 정책 (확정)").

### 요청 내용

1. 문항 선택을 시대·주제·유형·난이도 **비율 고정** 방식으로 변경한다.
   비율 값은 하드코딩하지 말고 설정 함수/상수 모듈 한 곳에서 관리한다.
2. 구체 비율 값은 기획 협의 사항이다. 초기값 협의 시 analytics 측과
   시대·유형 분포 기준을 맞춘다 (판정 집계 단위와 동일한 분류 체계 사용).
3. 일반 진단평가와 주간평가가 같은 선택 로직을 쓰는 현행 구조는 유지한다 —
   둘의 분포가 같아야 "진단 대비 변화" 비교가 성립한다.

## 제공 사항 (analytics 측)

- `complete_study_plan_block_by_id()` — 이미 제공·사용 중 (멱등)
- enqueue 서비스 함수 (요청 3) — `weekly_ai_reports` 구현 시 제공 예정.
  시그니처는 `(user_id, session_id, source_studyplan_id=None)` 형태로 협의
- `review_type` 도입 전 과거 데이터 fallback — analytics 내부에서 처리
  (완료된 diagnostic 세션 중 record 연결값이 있는 최신 1건, `weekly_review_ai_report_plan.md`)

## 검증 시나리오

1. 주간평가 블록에서 시작 → 세션 `review_type='weekly_review'`, records에 연결값 저장 확인
2. 일반 진단평가 시작 → `review_type` NULL 확인
3. 일반 진단평가 시작이 진행 중 주간평가 세션을 삭제하지 않는지 확인 (요청 2 확인 사항)
4. 주간평가 제출 → 블록 `isCompleted=true` + `weekly_ai_reports`에 `PENDING` row 1개 (요청 3 반영 후)
5. 같은 세션 중복 제출 → row가 늘지 않고 기존 row 유지
6. 주간평가 2회 반복 → 문항의 시대·유형 분포가 동일 비율인지 확인 (요청 4 반영 후)

## 일정 의존성

```text
DB: solve_sessions.review_type ALTER (DB 담당, 요청 진행 중)
  → 요청 1 (모델 선언) + 요청 2 (start 저장·삭제 범위) — 즉시 반영 가능
  → analytics: weekly_ai_reports 테이블·worker·enqueue 함수 구현
      → 요청 3 (제출 enqueue)
요청 4 (고정 비율 출제)는 위와 독립 — 비율 협의 후 언제든 반영 가능
```
