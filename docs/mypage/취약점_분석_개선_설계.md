# 취약점 분석 개선 설계

현행 취약점 분석의 네 가지 문제를 해결하는 설계 문서다.
구현 전 검토용이며 코드 변경은 포함하지 않는다.

**작업 범위: `app/analytics` 내부 + 프론트는 마이페이지와 오답률 상세 페이지까지 직접 수정한다.**
범위 밖은 다음 두 묶음이며 `docs/mypage/취약점_개선_협조_요청서.md`로 담당자에게 요청한다.

- 오답노트 취약 조합 로직 (`app/question`) — 공용 판정으로 교체 요청
- 결과 화면 3종의 "취약 TOP" 라벨 및 주변 설명 문구 (`templates/diagnosis/result.html`,
  `templates/study/result.html`, `templates/question/question_result.html`) —
  raw 오답률 표시는 유지하되 "취약 TOP"·"취약 유형"·"취약 시대" 등 "취약" 계열 문구를
  "오답 TOP"류로 조정 요청 (신규 "취약" 정의와의 용어 충돌 방지)

요청이 반영되기 전까지 해당 화면은 기존 기준·표현을 유지하며, 이 기간의 불일치는
알려진 한시적 상태로 둔다.

해결 대상:

| # | 문제 | 개선 |
|---|---|---|
| 1 | "취약"의 정의가 화면마다 다름 (카드 70% / 마이페이지 오답 1건 / 학습계획 가중 점수) | 취약 점수·판정 단일 정의 |
| 2 | 표본 보정 없음 (1문항 중 1오답 = 100%가 최상위 취약) | 신뢰구간 기반 보정 오답률 |
| 3 | 기간 불일치 (마이페이지 7일 vs 학습계획 전 기간) | 최근성 감쇠 가중 |
| 4 | 추세 없음 (개선 중인지 악화 중인지 구분 불가) | 주 단위 추세 판정 |

## 1. 핵심 설계: 취약 점수의 단일 정의

### 1.1 정의

모든 화면과 학습계획이 공유하는 취약 점수를 다음과 같이 정의한다.

```text
weakness_score = 보정 오답률(최근성 가중 표본 기준)      ← 0.0 ~ 1.0
```

즉 취약 점수는 새로운 합성 지표가 아니라, **"표본 수와 최근성을 반영해 신뢰할 수 있게 보정한
오답률"** 하나다. 합성 점수(오답률+시간+빈도 가중합)를 취약 정의로 쓰지 않는 이유는,
정의가 복잡할수록 사용자에게 "왜 이게 취약이죠?"를 설명할 수 없게 되기 때문이다.
시간 부담·출제 예상은 취약 정의가 아니라 **학습계획 우선순위 단계**(6장)에서만 결합한다.
"취약하다"와 "먼저 공부해야 한다"는 다른 질문이고, 이 분리가 1번 문제(정의 혼란)의 근본 해법이다.

### 1.2 상태 판정

```text
status =
  INSUFFICIENT  : 유효 표본 수 < min_sample          (판정 불가, 취약 목록 제외)
  WEAK          : weakness_score ≥ weak_threshold
  STABLE        : weakness_score ≤ stable_threshold
  NEUTRAL       : 그 외
```

초기 파라미터(8장에서 캘리브레이션):

| 파라미터 | 초기값 | 근거 |
|---|---:|---|
| min_sample | 3.0 (유효 표본) | 2문항 이하는 우연과 구분 불가 |
| weak_threshold | 0.50 | 보정 후 기준. raw 70%(14/20 규모)가 보정 시 ≈0.56이므로 그 부근을 취약 하한으로 |
| stable_threshold | 0.20 | raw 30%보다 낮게 잡는 이유: 보정이 점수를 전반적으로 끌어내리기 때문 |

주의: 기존 임계값 70/30은 raw 오답률 기준이라 **보정 점수에 그대로 쓸 수 없다.**
보정은 점수를 계통적으로 낮추므로(2.3 예시 표 참고) 임계값도 함께 낮춰 재보정해야 한다.

### 1.3 단일화 범위

판정 함수는 하나, 집계 단위는 화면 요구에 따라 다르다.

scope 요약 카드 6종을 만드는 `get_analysis_scope_overview`는 **현재 화면에 연결되어 있지 않다**
(`wrong_rate_detail` 뷰는 차트 데이터만 호출). 따라서 이번 개선 범위에서 카드 판정 정책은
다루지 않는다. 이후 카드 노출을 되살린다면 원칙은 하나다: **숫자와 판정을 서로 다른
데이터(snapshot 숫자 + 현재 판정)에서 만들지 않는다.** 현재 상태를 보여줄 카드라면 숫자·판정
모두 build_weakness_rows 산출에서, 기록을 보여줄 카드라면 둘 다 snapshot raw에서 만든다.
기준 기간이 다른 숫자와 배지를 한 카드에 섞으면 사용자에게 불일치로 보인다.

| 사용처 | 집계 단위 | 판정 |
|---|---|---|
| 마이페이지 취약 목록 | era + topic | 신규 판정 (동일 함수). **정렬은 weaknessScore(수치 미표시), 화면은 순위+등급 배지+"N문제 중 M오답" 개수+숫자 없는 막대 (2.4.1)** |
| 오답률 상세 **배지** (기간 기준) | era / topic / q_type 단일 분류 | 배지·판단 보류만 신규 판정. **표시·정렬은 raw 오답률 기준 (7.2/7.4 참조)** |
| 오답률 상세의 세션/기간 모달 | 세션·기간 내 분류 | raw 유지 (경로 2, 7.2 참조) |
| 세션별/기간별 차트 막대 | 세션·기간 집계 | raw 표시. 막대 색상 클래스는 raw 기준 시각 강조로 유지하되 `rawRateClass`로 개명 (7.2 참조) |
| 학습계획 복합 취약점 | era + topic + q_type | 신규 판정 (동일 함수) |
| AI 리포트 취약 분석 입력 | era + topic (+ q_type) | 신규 판정 (동일 함수) |
| (미노출) scope 요약 카드 | scope별 전체 | 이번 범위 제외. 노출 재개 시 위 원칙 적용 |

"단일 정의"란 **현재 상태를 판정하는 모든 곳**이 임계값·보정·감쇠·표본 기준을 한 함수로
공유한다는 뜻이다. 과거 기록 표시(기록 카드·세션 모달)는 판정이 아니라 사실 보존이므로
raw를 유지하며, 이는 예외가 아니라 역할 구분이다. 집계가 잘게 갈수록(복합) 표본이 줄어
INSUFFICIENT가 늘어나는데, 이는 버그가 아니라 "그 조합은 아직 판단할 데이터가 없다"는
올바른 신호다.

## 2. 표본 보정: Wilson 하한 (문제 2)

### 2.1 방식 선택

| 후보 | 방식 | 판단 |
|---|---|---|
| 라플라스 스무딩 | (wrong+1)/(total+2) | 구현 단순하지만 표본 크기에 따른 신뢰폭 반영이 거칠다. 1/1 → 0.67로 여전히 과대 |
| **Wilson score 하한 (채택)** | 이항 신뢰구간의 하한을 점수로 사용 | 표본이 적을수록 하한이 크게 내려가 과대평가를 구조적으로 방지. 정렬 문제(1/1 > 10/20)를 정확히 해결 |
| 베이지안 사전분포 | Beta(α,β) 사후 평균 | Wilson과 효과 유사하나 사전분포 선택 근거를 따로 설명해야 함 |

### 2.2 수식

```text
p̂ = effective_wrong / effective_total        (3장의 감쇠 가중 표본)
n  = effective_total
z  = 1.28                                     (80% 신뢰 수준)

adjusted_wrong_rate =
  ( p̂ + z²/2n − z·sqrt( p̂(1−p̂)/n + z²/4n² ) ) / ( 1 + z²/n )
```

z 선택: 1.96(95%)은 소표본을 과도하게 깎아 취약 감지가 늦어지고, 1.0(68%)은 보정이 약하다.
1.28(80%)을 초기값으로 하고 캘리브레이션 대상 파라미터로 둔다.

### 2.3 보정 효과 예시 (z=1.28, 감쇠 없음 가정)

| 기록 | raw 오답률 | 보정 오답률 | 판정(초기 임계값) |
|---|---:|---:|---|
| 1문항 중 1오답 | 100% | 37.9% | NEUTRAL — 하지만 표본 1 < 3 → **INSUFFICIENT** |
| 3문항 중 2오답 | 66.7% | 32.1% | NEUTRAL |
| 10문항 중 5오답 | 50.0% | 31.2% | NEUTRAL |
| 20문항 중 14오답 | 70.0% | 55.8% | **WEAK** |
| 20문항 중 4오답 | 20.0% | 11.0% | STABLE |

현행 문제였던 "1/1 오답(100%)이 14/20 오답(70%)보다 위"가 역전되어,
많이 풀고 많이 틀린 조합이 정확히 상위로 온다.

### 2.4 표시 원칙 — 보정값은 판정용, 표시값은 raw

기본 원칙은 화면에 보여주는 오답률 숫자에 **raw 값을 유지한다**는 것이다 ("5문제 중 3개 틀림 60%"는 사실이므로).
보정값은 판정·정렬·우선순위에만 쓴다. 사용자에게 계산 근거를 물어볼 수 없는 보정 수치를
raw 오답률처럼 **% 로** 보여주면 "내가 3개 틀렸는데 왜 32%라고 하지?"라는 혼란이 생긴다.
단, 표본 부족 항목에는 "풀이 수가 적어 아직 판단하지 않음" 표시를 병기한다.

#### 2.4.1 예외 — 마이페이지 취약 목록은 weaknessScore로 정렬하고 수치는 표시하지 않는다

마이페이지 취약 목록은 **비교 가능한 수치를 화면에 표시하지 않는다.** 표시는 raw 오답률(%)인데
정렬은 weaknessScore로 하면 "100%가 90%보다 아래"처럼 사용자가 보는 숫자와 순위가 어긋나
혼란을 준다. raw % 대신 "취약도 72" 같은 보정 점수 숫자를 헤드라인으로 써도, 임의 척도라
"72가 왜? 최대가 몇인데?"라는 새 의문을 만든다. 이 목록은 "취약점 분석"이고 **순위 자체가
우선순위를 뜻하므로**, 순위를 결정하는 값을 숫자로 노출하지 않고 순서·등급·근거로만 보여준다.

- **정렬**: `weaknessScore` DESC. 이 값은 **정렬에만 쓰고 화면에는 숫자로 표시하지 않는다.**
  새 합성 점수를 만들지 않고 **기존 weaknessScore를 그대로 재사용**한다(단일 정의 유지, 1.1).
- **수치 미표시**: raw 오답률 `%`도, 보정 점수(취약도) 숫자도 헤드라인으로 쓰지 않는다.
  화면에 서로 비교 가능한 숫자가 없으면 "100%가 90%보다 아래"류 모순이 원천적으로 불가능하다.
- **표시 요소**: ①순위(위→아래 = 먼저 학습할 것) ②취약 등급 배지(status 기반: 취약 / 관찰 필요 등)
  ③근거는 raw 사실을 **개수**로 병기 — 예: `조선·정치 — 10문제 중 9오답`(`%`가 아니라 개수.
  "최근 7일" 같은 기간 표현은 쓰지 않는다 — 판정 창이 감쇠 90일이라 기간을 약속하면 어긋난다, 3.3).
- **취약도 막대**: 목록이 `status == WEAK`만 노출(7.2)이라 배지가 모두 "취약"으로 같아 행 간 경중이
  안 드러난다. 이를 보완하려 **숫자 없는 막대**(길이 = weaknessScore에 비례)를 각 행에 함께 그린다.
  막대는 시각적 강도만 전달하고 눈금·수치 라벨은 붙이지 않는다.

즉 raw 사실("10문제 중 9오답")은 개수로 계속 보여주되, **비교 가능한 수치(오답률 %·취약도 점수)는
표시하지 않고** 순서·등급·막대로만 경중을 전달한다. 세션/기간 모달 등 "기록" 성격 화면(경로 2)은
기존 raw 표시를 유지한다.

## 3. 최근성: 지수 감쇠 가중 (문제 3)

### 3.1 방식 선택

| 후보 | 판단 |
|---|---|
| 기간 창 통일 (최근 28일만) | 단순하지만 경계 절벽이 생긴다. 29일 전 기록이 갑자기 0이 되고, 창 안에서는 27일 전과 어제가 동일 가중 |
| **지수 감쇠 (채택)** | 기록이 오래될수록 부드럽게 영향이 줄어든다. 절벽 없음. "예전에 틀렸지만 최근에 맞추는" 조합이 자연스럽게 하락 |

### 3.2 수식

```text
weight(record) = 0.5 ^ (days_ago / half_life)      half_life = 14일 (초기값)

effective_total = Σ weight
effective_wrong = Σ weight × is_wrong
```

- days_ago 기준 날짜는 세션의 recorded_date를 쓴다 (문항 단위 시각은 없음).
- half_life=14: 오늘 기록은 1.0, 2주 전 0.5, 4주 전 0.25, 8주 전 0.0625.
  시험 대비 주기(주 단위 평가)와 맞춘 초기값이며 캘리브레이션 대상.
- 계산 범위는 최근 90일로 제한한다(그 이전 weight < 0.012로 무의미, 쿼리 비용 절감).

### 3.3 파급 정리

- **학습계획(현행 전 기간)**: 감쇠 적용으로 자연히 최근 중심이 된다. 석 달 전 오답이
  계획 우선순위를 점유하는 문제가 해소된다.
- **마이페이지(현행 7일 창)**: **확정 — 7일 하드 창을 없애고 판정·정렬·표시를 감쇠 표본으로
  통일한다.** 7일 창 유지 시 표본 부족(INSUFFICIENT) 항목이 급증해 목록이 자주 비고,
  절벽 효과와 화면 간 기준 분열이 남는 것이 근거다. 화면 문구는 세 곳을 함께 정리한다:
  ① 라벨 "최근 7일 요약" → "최근 학습 기준" (+툴팁 "최근 기록일수록 크게 반영돼요").
  라벨에서 숫자 기간을 뺀다 — 감쇠에는 경계 기간이 없어 기간을 약속하면 어긋난다.
  ② 근거 개수 문구는 기간 표현을 제거한다 ("10문제 중 9오답", 90일 창 raw 건수 — 2.4.1).
  ③ 오답률 상세의 기준 안내 문구(7.2 상세 기준)는 현행 확정안 유지.
- INSUFFICIENT 판정도 effective_total 기준으로 한다(raw 건수가 아니라). 오래된 기록만 있는
  조합은 표본이 있어도 "지금은 판단 근거 부족"으로 처리되는 것이 의도된 동작이다.

## 4. 추세 판정 (문제 4)

### 4.1 정의

```text
현재 구간: 최근 14일의 보정 오답률 (감쇠 없이, 구간 내 균등)
비교 구간: 그 이전 14일의 보정 오답률

delta = 현재 − 비교

trend =
  UNKNOWN    : 어느 한쪽 구간의 표본 < min_sample
  WORSENING  : delta ≥ +trend_threshold (+0.10)
  IMPROVING  : delta ≤ −trend_threshold (−0.10)
  FLAT       : 그 외
```

- 구간 폭 14일: 주간평가 2회분으로, 1회분(7일)은 표본이 부족해 UNKNOWN이 과다해진다.
- 구간 비교에는 감쇠를 쓰지 않는다. 감쇠는 "현재 상태" 추정용이고, 추세는 "구간 간 변화"라
  구간 내 균등 가중이 맞다. 두 목적에 같은 장치를 쓰면 해석이 꼬인다.
- delta 비교에도 보정 오답률(Wilson)을 쓴다. raw로 비교하면 소표본 구간의 요동이 추세로 오인된다.

### 4.2 활용

| 사용처 | 방식 |
|---|---|
| 화면 배지 | WEAK + WORSENING이면 강조 표시 (예: "취약·악화") |
| 학습계획 우선순위 | 6장의 trend_bonus 가산 |
| AI 리포트 | Diagnostician의 trend 필드 입력 (별도 계산 없이 이 값을 그대로 사용) |

주간 AI 리포트 설계(`docs/mypage/weekly_review_ai_report_plan.md`)의 취약 개념 추세 입력은
이 함수의 산출을 그대로 받는다. 취약점 분석 개선이 곧 리포트 입력 품질 개선이다.

## 5. 통합 산출 스키마

모든 사용처가 받는 조합별 산출 행:

```json
{
  "groupKeyId": "era=조선|topic=정치|q_type=역사 자료의 분석 및 해석",
  "groupKey": [["era", "조선"], ["topic", "정치"], ["q_type", "역사 자료의 분석 및 해석"]],
  "group": {"era": "조선", "topic": "정치", "qType": "역사 자료의 분석 및 해석"},
  "raw":       {"total": 20, "wrong": 14, "wrongRate": 0.70, "avgTimeSec": 55},
  "effective": {"total": 16.2, "wrong": 11.9},
  "weaknessScore": 0.558,
  "status": "WEAK",
  "trend": {"value": "WORSENING", "delta": 0.18,
            "current": {"total": 9, "adjustedRate": 0.61},
            "previous": {"total": 8, "adjustedRate": 0.43}},
  "insufficientReason": null
}
```

raw와 effective를 모두 담는 이유: 표시(2.4)는 raw, 판정은 effective/보정 기반이라
두 값이 항상 함께 다녀야 화면 구현에서 혼용 실수가 나지 않는다.

**표기 규칙**: `status`는 대문자 도메인 값(WEAK/NEUTRAL/STABLE/INSUFFICIENT)이다.
화면용 소문자 클래스 키(weak/neutral/stable/insufficient)의 필드명은 **기존 데이터 묶음의
관례를 따른다** — display rows(예: `build_wrong_rate_display` 산출)는 `status_class`(snake_case),
chart/JSON형 payload(예: 차트 막대, 모달 데이터)는 `statusClass` 또는 `rawRateClass`(camelCase).
새 묶음을 만들 때도 그 묶음이 흐르는 경로의 기존 관례를 따르고, 한 묶음 안에서 두 표기를
섞지 않는다. 대문자→소문자 변환은 각 묶음의 직렬화 지점 한 곳에서만 수행하며,
서비스 로직·비교문은 항상 대문자 도메인 값을 쓴다.

키 필드는 두 개이며 역할이 다르다. 둘 다 build_weakness_rows가 생성하고,
호출부는 label이나 group dict에서 키를 재조립하지 않는다.

- `groupKeyId` (**매칭용, canonical string**): `"field=정규화값"`을 `|`로 이은 문자열.
  실제 매칭 키는 항상 이것이다 — Python에서는 dict 키로, JS에서는 문자열 비교로 그대로
  쓸 수 있다 (list/배열은 Python dict 키가 못 되고 JS에서 값 비교도 안 되기 때문).
  값에 `|`나 `=`가 포함될 가능성이 있으므로 생성 함수 한 곳(build_group_key_id)에서만 만들고
  이스케이프 규칙도 거기서 처리한다.
- `groupKey` (**구조 표현용**): `[field, 정규화값]` 쌍의 목록. 단일 분류면 쌍 1개,
  복합이면 group_fields 순서대로 쌍 3개. 필드별 접근·표시가 필요할 때 쓴다.

**표시명(label) 규칙**: 정규화값 → 화면 표시명 변환은 taxonomy 상수 모듈
(`app/analytics/service/taxonomy.py`) 한 곳에서만 수행한다. 역사 분류는 변경이 없으므로
DB 참조 테이블이 아니라 상수 모듈로 관리한다 — 배포 없이 값을 바꿀 운영 주체가 없어
DB의 장점을 쓸 일이 없고, 시딩·조회·빈 테이블 실패 케이스 비용만 남기 때문이다.
"하드코딩 금지"의 본질은 분산 금지이며, 한 모듈에 모인 도메인 상수는 위반이 아니다.
미분류 폴백과 복합 조합 표기("조선 · 정치 · 사료형" 조립)도 이 모듈이 담당하고,
각 화면·서비스는 label 문자열을 자체 생성하지 않는다.

## 6. 학습계획 우선순위와의 결합

취약 정의(1~4장)와 우선순위 계산은 분리 유지한다. 변경점만 정리하면:

```text
현행: priorityScore = wrongRate        × W_weak
                    + predictionScore  × W_pred
                    + timeBurden       × W_time

개선: priorityScore = weaknessScore    × W_weak      ← raw 오답률을 보정 점수로 교체
                    + predictionScore  × W_pred
                    + timeBurden       × W_time
                    + trendBonus                      ← 신규
```

- trendBonus: WORSENING +0.08, IMPROVING −0.04, FLAT/UNKNOWN 0 (초기값).
  악화 가산을 개선 감산보다 크게 두는 이유: 악화 방치 비용이 개선 조합을 한 번 더 보는
  비용보다 크기 때문(손실 회피 비대칭).
- **포함 조건 변경**: 현행 "오답 1건 이상" → "status가 INSUFFICIENT가 아니고
  weaknessScore > stable_threshold". 안정 조합과 판단 불가 조합이 계획 후보에서 빠진다.
- **후보 고갈 폴백**: 위 조건(WEAK·NEUTRAL 포함)으로 후보가 부족하면(예: 신규 사용자)
  단계적으로 완화한다. ① INSUFFICIENT 중 오답 존재 조합 포함 → ② 출제 예상만으로 구성.
  (기본 조건이 이미 NEUTRAL을 포함하므로 "NEUTRAL 포함" 단계는 존재하지 않는다.)
  폴백 단계는 계획 블록에 기록해 두어(planSource 속성) 나중에 품질을 추적할 수 있게 한다.
  **planSource는 현행 블록 생성 스키마(studyplan.py의 블록 dict)에 없는 신규 필드다.**
  블록 생성부에 필드 추가가 필요하며(값: normal / fallback_any_wrong /
  fallback_prediction_only), 기존 블록에는 없는 필드이므로 조회 코드는 없으면 normal로 간주한다.
  **폴백 고지**: 폴백 사실은 내부 기록(planSource)에 그치지 않고 화면에도 고지한다 —
  fallback_prediction_only로 구성된 계획에는 "아직 학습 기록이 부족해 출제 예상 중심으로
  구성했어요"류 문구를 표시한다 (신규 사용자 표본 부족 고지, 11장 확정 결정 참조).
- 남은 기간별 가중치 표(short/medium/long)와 정렬 tie-breaker는 현행 유지.

`build_wrong_rate_display` 교체의 상세 기준 (표에서 분리):

- **두 묶음의 매칭 키**: 표시명(label)이 아니라 5장의 `groupKeyId`(canonical string)로 매칭한다 —
  단일 분류 화면은 필드 1개(예: `"era=조선"`), 복합 화면은 필드 3개. 즉 build_weakness_rows의
  group_fields와 동일한 필드 집합이 키가 된다. 현행 `get_wrong_rate_group_stats()` 반환이
  label 중심이므로 반환 행에 groupKeyId(매칭용)를 추가해야 하며 — 구조 표현이 필요하면
  groupKey도 함께 — 이렇게 해야 `미분류`·표시명 충돌에서 매칭이 깨지지 않는다.
- **화면 반영 경로**: 현재 템플릿은 era/type/topic stats의 status_label/class를 직접 렌더링하지
  않고 도넛 요약만 보여주므로, 이 함수만 바꾸면 화면에 변화가 보이지 않는다. 함께 수정한다:
  ① `build_wrong_rate_donut_summary`(display.py:573)의 segment에 `status/trend/weaknessScore`를
  전달해 세그먼트 라벨·툴팁에 배지를 표시한다. 단, 도넛 세그먼트 정렬은 "오답 수 비중" 시각화
  목적이므로 wrong 기준을 유지한다. **"기타" 세그먼트(표시 개수 초과 항목의 묶음, display.py:594)는
  여러 조합의 합이라 단일 status/trend가 성립하지 않으므로 배지를 생략한다** — 배지는
  개별 항목 세그먼트에만 붙인다.
  ② 분류별 stats 영역을 status 배지와 함께 렌더링하도록 템플릿에 노출을 추가한다
  (직접 수정 범위 프론트 작업). **정렬은 raw 오답률 DESC를 유지**하고, weaknessScore는
  정렬이 아니라 배지 표시에만 쓴다. 표시 숫자와 순위가 같으므로 "100%가 90%보다 아래"가 없다.
- **표시 목록 기준**: 이 화면의 목록은 "최근 7일 raw 집계에 존재하는 항목"으로 유지하고,
  90일 weakness rows는 그 항목들의 **배지에만** 쓴다. 90일 기준으로 취약하지만 최근 7일에
  풀이가 없는 항목은 이 화면에 나타나지 않는다 — 그런 항목의 노출은 감쇠 기준으로 목록을
  만드는 마이페이지 취약 목록이 담당한다 (화면 역할 분담).

### 7.3 데이터·성능

- **DB 스키마 변경 없음.** 신규 판정 계산은 전부 SolveRecords에서 read-time으로 수행한다.
- **두 경로를 명시적으로 분리한다.** Analytics snapshot에는 overall/era/type/topic의
  raw 집계만 저장되어 있고 날짜별 분포가 없으므로, snapshot만으로는 감쇠·추세를 계산할 수 없다.
  - 경로 1 (신규 판정): 현재 상태를 보여주는 화면(마이페이지 취약 목록, 오답률 상세 배지,
    학습계획, AI 리포트 입력)은 SolveRecords에서 build_weakness_rows로 계산한다.
  - 경로 2 (raw 기록 표시): "당시/해당 범위의 사실 기록"이 목적인 화면은 raw 값과
    기존 raw 임계값 기준을 유지한다. 데이터 원천에 따라 둘로 나뉜다.
    - 경로 2-a (snapshot raw): 저장된 Analytics snapshot을 그대로 표시 (세션 결과,
      study_plan_base/result 비교 등 저장 시점 기록)
    - 경로 2-b (SolveRecords raw 재집계): 세션/기간 상세 모달처럼 SolveRecords를
      해당 범위로 다시 집계하되 보정·감쇠 없이 raw로 표시
  - snapshot에 보정값을 저장하는 방식은 채택하지 않는다. 파라미터를 나중에 조정하면
    과거 저장값과 어긋나기 때문이다.
- 쿼리는 최근 90일 필터 + 그룹 집계가 기본이지만, 감쇠(일 단위 재집계)와 추세(구간 2개 추가
  집계) 때문에 현행 단순 집계보다 쿼리 수·Python 처리량이 늘 수 있다. **현행 동급을 목표로
  하되, 캘리브레이션(8장) 시점에 화면별 쿼리 수와 처리 시간을 실측해 확인한다.**
  필요 시 일 단위 그룹 집계 1회로 감쇠·추세를 함께 계산하는 형태로 쿼리를 합친다.

## 8. 파라미터 캘리브레이션 절차

초기값은 전부 가설이므로, 배포 전 실데이터로 다음을 확인한다.

1. **분포 확인**: 전체 사용자 × (era,topic,q_type) 조합의 weaknessScore 분포를 뽑아
   WEAK/NEUTRAL/STABLE/INSUFFICIENT 비율을 확인한다. WEAK가 5% 미만이면 임계값이 과하고,
   40% 이상이면 느슨한 것이다 (경험적 목표: 조합의 10~25%가 WEAK).
2. **정렬 검증**: 현행 기준과 신규 기준의 상위 10개 취약 목록을 사용자 표본별로 나란히 놓고,
   "1문항 100%"류가 상위에서 사라졌는지, 직관적으로 납득 가능한지 육안 검수한다.
3. **추세 안정성**: 주 단위로 trend를 재계산했을 때 FLAT↔WORSENING이 매주 뒤집히는 조합
   비율을 확인한다. 과도하면 trend_threshold를 올린다.
4. 시뮬레이션 스크립트는 일회성 검증 도구로 만들되 서비스 코드와 분리한다.

### 9.2 회귀

- 기존 화면 API 응답: 기존 필드 값 의미는 유지하되, 신규 상태값(`insufficient`)과 신규 필드
  (`weaknessScore`, `trend`)가 **추가**된다. 스키마 불변이 아니라 하위 호환 확장이다.
  **예외 1건**: 차트 막대의 `statusClass` → `rawRateClass`는 필드명 **변경**(breaking)이다.
  서버와 템플릿을 반드시 같은 배포 묶음으로 동시 수정한다 (7.2 참조).
- **마이페이지 프론트 (직접 수정 범위)**:
  - 취약 목록에서 **오답률 % 등 비교 가능한 수치를 제거한다.** weaknessScore DESC로 정렬하되
    그 점수도 화면에 숫자로 노출하지 않는다. 대신 ①순위 ②취약 등급 배지 ③raw 사실을 **개수**로
    ("N문제 중 M오답") ④**숫자 없는 취약도 막대**(길이 ∝ weaknessScore, 눈금·라벨 없음)로 표시한다 (2.4.1).
    회귀 검증 항목: (a) 화면에 오답률 %·취약도 점수 숫자가 노출되지 않는가, (b) 정렬이 weaknessScore DESC인가,
    (c) "100% 항목이 90% 항목보다 아래" 같은 순서 역전 혼란이 재현되지 않는가(비교 수치 부재로 성립 불가),
    (d) 막대 길이가 정렬 순서와 단조 일치하는가.
  - `insufficient` 상태 라벨/스타일 추가 — 문구: "풀이 수가 적어 아직 판단하지 않아요"
    (틀린 상태가 아니라 데이터 부족이므로 중립 회색 계열)
  - 취약 목록 빈 상태 문구: "아직 취약으로 판단할 데이터가 부족해요.
    문제를 더 풀면 분석이 정확해져요."
  - `trend` 표시: weak+worsening은 "취약 · 악화" 강조, improving은 "개선 중", flat/unknown은 생략
- **오답률 상세 화면 프론트 (직접 수정 범위)**: 현재 JS의 weak/stable/empty 라벨 매핑에
  `insufficient`(위와 동일 문구·스타일)와 `trend` 표시를 추가한다. 서버와 같은 배포 묶음으로
  반영하므로 다운그레이드 매핑은 필요 없다.
  - **라벨 맵 분리**: 현재 공용 `statusLabels`(weak→"취약")가 세션/기간 모달 카드에도 쓰인다
    (wrong_rate_detail.html:358, 746). 그대로 두면 raw 기록 경로에 다시 "취약" 문구가 섞이므로,
    "신규 판정용 라벨 맵"(취약/안정/판단 보류 등)과 "raw 기록용 라벨 맵"(오답률 높음/오답 TOP 등)을
    분리하고 모달 쪽은 후자를 쓴다.
  - **기준 안내 문구**: 표시·정렬은 최근 7일 raw 오답률로 일치하고, 배지의 취약 판단만 90일 감쇠 기준이다.
    화면에 "취약 배지는 최근 학습(가중) 기준" 보조 문구 또는 툴팁을 추가해 배지와 %의 기준 차이를 설명한다.
    (정렬은 표시 %와 같으므로 순서 관련 안내는 불필요하다.)
- 오답률 상세 화면 회귀 (7.2 상세 기준 반영 확인):
  - 분류별 stats 영역이 status 배지와 함께 렌더링되는가
  - stats 목록 정렬이 raw 오답률 DESC(동률 시 오답 수·풀이 수) 기준인가
  - "100% 항목이 90% 항목보다 아래"인 순서 역전이 없는가
  - 도넛 세그먼트 정렬은 wrong 기준으로 유지되는가
  - "기타" 세그먼트에 배지가 붙지 않는가
- 학습계획 생성 E2E: 신규 사용자 / 소량 기록 / 다량 기록 3개 프로필.
  각 프로필에서 블록의 `planSource` 필드가 기대 폴백 단계와 일치하는지 확인
  (planSource 없는 기존 블록의 하위 호환 — normal 간주 — 포함)

  보강**한다. ① Wilson 하한은 소표본일수록 점수를 낮추는 보수 보정이라 성급한 취약 판정을
  막는 방향으로 작동하고 ② `effective_total < min_sample`이면 INSUFFICIENT로 판정 자체를
  보류하며 ③ 후보 고갈 시 학습계획은 폴백(6장)으로 동작한다. 고지는 두 곳: 마이페이지
  안내 문구(아래 INSUFFICIENT 항목)와 폴백 계획 문구(6장 폴백 고지).

- INSUFFICIENT 항목의 화면 노출: **숨김 + 안내 문구**. 별도 "데이터 부족" 섹션은 만들지
  않는다. 마이페이지 취약 목록에는 "아직 충분히 풀지 않은 조합은 표시되지 않아요"류
  안내 문구를 두고(9.2 빈 상태 문구와 함께 관리), 상세 확인은 오답률 상세의
  "판단 보류" 배지가 담당한다.
- trend UNKNOWN 조합의 학습계획 취급: **trendBonus 0으로 포함, 별도 표시 없음**.
  UNKNOWN은 "추세를 모른다"이지 "취약하지 않다"가 아니므로 후보에서 빼지 않는다
  (6장 포함 조건은 status·weaknessScore 기준 그대로).
