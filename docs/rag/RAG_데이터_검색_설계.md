# RAG 데이터·검색 설계

## 1. 저장 구조

RAG 본문은 PostgreSQL의 `rag.document_chunks`에 저장합니다. 행 하나는 검색·인용의 최소 단위인 청크입니다.

| 필드 | 역할 |
|---|---|
| `chunk_id` | 청크의 고유 키 |
| `document_id` | 같은 원문에서 나온 청크 묶음 키 |
| `source_type`, `source_name` | 출처 구분과 표시명 |
| `title`, `chunk_text` | 검색·LLM 컨텍스트에 쓰는 본문 |
| `metadata` | 시대, 분야, 분류 경로, 키워드, 원본 URL, 별칭 등 구조화 정보 |
| `search_tokens`, `search_vector` | MeCab 기반 BM25 검색용 토큰과 FTS 인덱스 |
| `embedding` | 의미 검색용 pgvector 벡터 |

연표는 구조와 용도가 달라 `rag.history_timeline`에 분리합니다. 연대·순서·시기 질문에서만 추가 근거로 조회합니다.

## 2. 원천별 전처리 원칙

사료·신편 한국사는 본문을 약 1,200자 단위로 나누고 일부 겹침을 둡니다. 제목·시대·분야·분류 경로는 메타데이터로 정규화합니다.

이미지 자료는 설명과 URL 메타데이터를 한 청크로 저장합니다. 이미지 검색은 제목·메타데이터 중심의 별도 흐름을 사용하므로 벡터를 만들지 않습니다.

백과사전은 항목(`eid`)을 문서 단위로 사용합니다. 모든 청크 앞에 제목·정의·별칭을 넣습니다. `headword`, `origin`, `articleAliases`는 `metadata.aliases`와 `chunk_text`에 함께 보존합니다. 별칭 전용 컬럼만 두면 현재 BM25·벡터 검색이 읽지 않으므로 검색 텍스트에도 넣는 것이 필수입니다.

## 3. 적재와 변경 반영

적재는 `chunk_id` 기준 UPSERT입니다. `chunk_text`가 이전 값과 같으면 기존 임베딩을 유지하고, 달라지면 해당 청크의 임베딩만 `NULL`로 비워 재생성합니다.

따라서 별칭·본문을 수정한 뒤에는 전체 전처리·적재 명령을 실행해도 변경된 청크만 API 임베딩 비용과 시간이 듭니다. 원천에서 청크가 삭제된 경우에만 `--delete-missing`으로 DB 정합성을 맞춥니다.

## 4. BM25 운영

MeCab BM25는 `search_tokens`, `search_vector`, GIN 인덱스를 사용합니다. 기존 청크에 BM25 구조만 추가·갱신할 때는 벡터 재임베딩 없이 아래 명령을 실행합니다.

```powershell
.\.venv\Scripts\python.exe etl\preprocessing\history\embedding\embed_chunks_to_pgvector.py --setup-mecab-bm25
```

새 DB에서 청크를 처음 적재하면 이 구조는 자동으로 생성됩니다.

## 5. 검색 흐름

```text
질문 정규화
  → 핵심어 추출
  → 벡터 후보 + MeCab BM25 후보
  → RRF 결합
  → 개요 질문의 제목 다양화·핵심어 우선 정렬
  → 선택적 CrossEncoder 재순위화
  → 상위 청크를 LLM 근거로 전달
```

- 일반 개념 질문은 pgvector와 BM25를 함께 사용합니다.
- 개요형 질문은 제목·본문에 핵심어가 있는 청크를 우선하고 같은 제목의 중복을 줄입니다.
- 비교 질문은 두 대상이 서로 다른 청크에 있을 수 있어 BM25 후보를 넓게 수집합니다.
- 이미지 질문은 벡터 검색을 우회합니다.
- 연표 의도가 있으면 `rag.history_timeline` 결과를 추가합니다.

## 6. 답변 경계

LLM은 검색된 청크 안의 내용만 답변합니다. 따라서 특정 인물의 이칭·관계가 답변에 나오려면 그 사실이 반드시 `chunk_text`에 포함되어 검색 후보로 전달되어야 합니다.

챗봇의 개념 답변은 구조화된 표 형식으로 생성하며, 스트리밍 시에는 제목·섹션·표 행을 순서대로 전송합니다. 검색 데이터와 출력 형식은 분리되어 있으므로, 출력 프롬프트 변경은 데이터 재임베딩을 요구하지 않습니다.
