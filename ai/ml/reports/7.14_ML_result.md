# 7.14 ML 결과 정리

작성일: 2026-07-14

## 1. 진행 목적

기존 `ml_han_features_v1` 기반 ML 실험에서 `topic`, `topic_train` 성능이 낮게 나오는 문제가 있었다. 원인은 모델 구조 자체보다 **전처리 라벨 품질과 feature 품질 문제**일 가능성이 높다고 판단했다.

따라서 오늘 작업의 목표는 다음이었다.

```text
1. GPT 상위 모델로 시대/주제/통합 주제 재라벨링
2. 새 feature 데이터 ml_han_features_v2 생성
3. 같은 KLUE/RoBERTa 조건으로 재학습
4. 기존 결과와 비교
5. 신뢰도 검증을 위해 core/keyword 제거 실험 수행
```

## 2. 데이터 전처리 방식

### 기존 v1 전처리

기존 `ml_han_features_v1`은 규칙 기반 전처리로 생성되었다.

- 시대(`era`): 키워드 사전, 인물-시대 매핑, override, 문제 번호 fallback 사용
- 주제(`topic`): 기존 topic 후보, topic_type, 키워드 매칭 사용
- 통합 주제(`topic_train`): `topic`을 만든 뒤 규칙으로 통합
- 핵심 개념(`core_concept`): 기존 topic 또는 키워드 기반 추출

장점은 재현성과 비용 절감이지만, 복합 문항이나 경계가 애매한 문항에서 라벨 노이즈가 발생했다.

### 신규 v2 전처리

`ML_han_v1.json` 1600건 전체를 `gpt-5.6-terra`로 재라벨링했다.

생성된 주요 컬럼:

- `era`
- `topic`
- `topic_train_v1`
- `topic_train_v2`
- 최종 `topic_train`
- `question_type`
- `question_subtype`
- `core_concept`
- `label_confidence`
- `ambiguous_flag`
- `label_reason`

이후 다음 파일과 폴더를 생성했다.

```text
ai/ml/output/ml_han_features_v2.json
ai/ml/output/ml_han_features_v2.csv
ai/ml/output/split_v2/
ai/ml/output/split_topic_merged_v2/
ai/ml/output/eval_splits_v2/
ai/ml/output/eval_splits_with_core_v2/
```

## 3. v1 -> v2 변경량

1600건 기준 변경량은 다음과 같다.

| 항목 | 변경 건수 | 비율 |
|---|---:|---:|
| `era` | 520 | 32.5% |
| `topic` | 652 | 40.8% |
| `topic_train` | 667 | 41.7% |
| `core_concept` | 1559 | 97.4% |

이 결과는 기존 성능 저하의 핵심 원인이 **모델이 아니라 라벨/feature 품질**에 있었을 가능성을 보여준다.

## 4. 학습 조건

공통 학습 조건은 다음과 같다.

| 항목 | 값 |
|---|---|
| model | `klue/roberta-base` |
| max length | 512 |
| batch size | 16 |
| learning rate | `5e-6` |
| max epochs | 30 |
| patience | 3 |
| class weight | True |
| cross validation | 3-fold |
| random state | 42 |

`learning_rate=5e-6`은 기존 BERT fine-tuning에서 자주 쓰이는 `2e-5`보다 4배 작다. 학습 속도는 느리지만, 현재처럼 train 데이터가 약 1200건으로 작고 라벨 경계가 애매한 데이터에서는 더 안정적으로 학습된다.

## 5. 평가 split

### split_era_topic_train_stratified_v1

`era + topic_train` 조합 분포를 train/test에 비슷하게 유지한 층화 split이다.

목적:

```text
모델이 라벨 체계를 전반적으로 잘 학습했는지 확인
특정 다수 클래스만 맞춰서 성능이 좋아 보이는 문제 완화
```

### split_time_v1

과거 회차를 train으로, 71~78회차를 test로 사용하는 시간 기준 split이다.

목적:

```text
최신 회차에 대한 일반화 성능 확인
실제 서비스/미래 문항 예측 상황에 가까운 평가
```

## 6. 평가 지표

### Accuracy

전체 문항 중 맞춘 비율이다.

```text
accuracy = 맞춘 개수 / 전체 개수
```

단점은 클래스 불균형이 심하면 다수 클래스만 잘 맞춰도 높게 나올 수 있다는 점이다.

### Macro F1

각 클래스의 F1을 같은 비중으로 평균낸 값이다.

```text
macro F1 = 각 라벨 F1의 단순 평균
```

소수 클래스 성능까지 공정하게 보기 좋다. 이번 실험에서는 가장 중요한 지표로 사용했다.

### Weighted F1

각 클래스 F1을 실제 데이터 개수 비율로 가중 평균한 값이다.

```text
weighted F1 = 클래스별 F1 * 클래스 support 비율
```

다수 클래스 성능의 영향을 더 많이 받는다.

### CV macro F1 mean

train 데이터 내부에서 3-fold cross validation을 수행했을 때의 macro F1 평균이다.

```text
CV macro F1 mean
= train 데이터만 3번 나눠 검증한 macro F1 평균
```

최종 test 한 번만 잘 나온 것인지, train 내부 검증에서도 안정적인지 판단하는 데 사용했다.

## 9. target별 해석

### topic_train

`topic_train`은 5개 통합 주제 라벨이다.

```text
사건 / 인물 / 정치 / 문화 / 제도
```

stratified 결과:

```text
accuracy: 0.8603
macro F1: 0.8541
weighted F1: 0.8621
```

time split 결과:

```text
accuracy: 0.8175
macro F1: 0.8089
weighted F1: 0.8164
```

stratified뿐 아니라 최신 회차 평가에서도 macro F1 0.8 이상을 유지했다. 따라서 `topic_train` 모델은 최종 서비스/추천용 주제 모델로 사용 가능성이 높다.

주요 오분류는 `사건/정치/제도` 경계에서 발생했다.

### era

`era`는 시대 라벨이다.

stratified 결과:

```text
accuracy: 0.9302
macro F1: 0.9266
weighted F1: 0.9301
```

시대 분류는 매우 안정적이다. 다만 `고조선`, `초기 국가`, `선사 시대`처럼 support가 작은 클래스는 표본 수가 적어 점수를 과신하면 안 된다.

후반 epoch에서 약한 과적합 징후는 있었지만, CV 성능과 test 성능이 모두 높아 심한 오버피팅은 아니라고 판단했다.

### topic

`topic`은 10개 세부 주제 라벨이다.

```text
경제 / 군사 / 문화 / 사건 / 사상·종교 / 사회 / 외교 / 인물 / 정치 / 제도
```

결과:

```text
accuracy: 0.8130
macro F1: 0.7056
weighted F1: 0.8194
```

`topic_train`보다 낮은 이유는 다음과 같다.

- 라벨 수가 5개에서 10개로 증가
- 소수 클래스가 많음
- `정치/사회/외교/군사/경제` 경계가 애매함
- `문화/사상·종교`, `사건/군사`, `정치/제도`가 자주 섞임

특히 `macro F1`과 `weighted F1` 차이가 크다.

```text
macro F1: 0.7056
weighted F1: 0.8194
```

이는 다수 클래스는 잘 맞추지만, 소수 클래스 성능이 낮다는 의미다.

따라서 `topic` 모델은 최종 추천용보다는 **세부 분석/보조 정보용**으로 사용하는 것이 적절하다.

## 10. 신뢰도 검증 결과

성능 향상이 `core_concept` 힌트 때문인지, 라벨 품질 개선 때문인지 확인하기 위해 입력 feature를 줄여가며 실험했다.

### text_with_core

```text
입력 = 문항 텍스트 + [키워드] + [Core Concept]
macro F1: 0.8541
```

### text = input + keyword

```text
입력 = 문항 텍스트 + [키워드]
macro F1: 0.8683
```

`Core Concept` 블록을 제거했는데 오히려 성능이 소폭 상승했다. 즉 성능 향상이 `Core Concept` 하나에만 의존한 것은 아니다.

### input_text only

```text
입력 = 문항 지문 + 질문
macro F1: 0.7629
```

키워드까지 제거하면 성능이 하락했다. 하지만 기존 v1 계열보다 여전히 좋은 편이다.

해석:

```text
v2 라벨 품질 개선 효과는 확실히 존재한다.
다만 [키워드] feature가 성능에 크게 기여한다.
Core Concept 추가 효과는 크지 않거나 keyword와 중복되었을 가능성이 있다.
```

## 11. Cross Validation 그래프 해석

CV loss 그래프는 fold별 train loss와 validation loss를 보여준다.

```text
점선 = train loss
실선 = validation loss
```

좋은 패턴:

```text
train loss와 validation loss가 함께 내려감
validation loss가 최저점을 찍은 뒤 정체 또는 상승
그 최저점 근처가 best epoch
```

이번 실험들은 대부분 다음 패턴을 보였다.

```text
초반: train/validation loss 함께 감소
중반: validation loss 최저점 도달
후반: train loss는 계속 감소, validation loss는 정체 또는 상승
```

이는 후반부에 약한 과적합이 생긴다는 뜻이다. 하지만 `patience=3` early stopping을 사용했고, final epoch도 CV best epoch 평균에 맞춰 설정되어 심한 오버피팅은 아니라고 판단했다.

## 12. class weight 정리

`class weight`는 학습 시 클래스 불균형을 보정하기 위한 파라미터다.

계산식:

```text
class_weight_c = N / (K * n_c)
```

의미:

```text
N   = 전체 학습 샘플 수
K   = 클래스 개수
n_c = 클래스 c의 샘플 수
```

데이터가 적은 클래스일수록 weight가 커지고, 해당 클래스를 틀렸을 때 loss가 더 크게 반영된다.

`class weight`와 `weighted F1`은 다르다.

| 항목 | class weight | weighted F1 |
|---|---|---|
| 사용 시점 | 학습 중 | 평가 후 |
| 목적 | 소수 클래스 학습 보정 | 클래스 비중을 반영한 성능 평가 |
| 점수 계산에 직접 영향 | 없음 | 있음 |
| 모델 학습에 영향 | 있음 | 없음 |

`class weight=True`는 점수 계산식을 바꾸는 것이 아니라, 모델이 학습되는 방식을 바꾼다.

## 13. 현재 결론

### 최종 모델 후보

| 목적 | 추천 |
|---|---|
| 통합 주제 예측 | `topic_train` 모델 |
| 시대 예측 | `era` 모델 |
| 세부 주제 분석 | `topic` 모델 |
| 서비스/추천 기준 | `topic_train + era` 조합 |

현재 가장 안정적인 구조는 다음이다.

```text
문항 입력
-> era 모델로 시대 예측
-> topic_train 모델로 통합 주제 예측
-> topic 모델은 세부 분석/보조 정보로 사용
```

### 성능 향상의 주된 이유

1. GPT 상위 모델 기반 재라벨링으로 라벨 노이즈가 줄었다.
2. `topic_train`이 문항 중심 개념 기준으로 더 일관되게 정리되었다.
3. `[키워드]` feature가 모델에게 강한 힌트로 작동했다.
4. `learning_rate=5e-6`과 class weight로 작은 데이터셋에서도 안정적으로 학습했다.

### 남은 한계

1. v2 전처리 단계에서 GPT가 정답 선택지를 참고했다.
2. `[키워드]` feature의 영향이 크다.
3. 완전한 신규 문항 예측 환경에서는 `answer_choice` 없이 feature를 만들어야 한다.
4. `topic` 세부 라벨은 소수 클래스와 경계 문제로 아직 불안정하다.

## 14. 개선 방안

### 1. answer_choice 제외 v2.1 전처리

가장 엄밀한 추가 검증이다.

```text
지문 + 질문 + 선택지만 사용
정답 선택지 제외
-> GPT era/topic/topic_train/core_concept 생성
-> 재학습
```

이 결과도 좋다면 실제 신규 문항 예측 신뢰도가 크게 올라간다.

### 2. topic 오답 검토

`topic`의 약한 클래스:

```text
사회 / 외교 / 정치 / 군사 / 사상·종교
```

이 라벨들은 기준을 더 명확히 정하거나, 최종 서비스에서는 `topic_train`으로 통합해 사용하는 것이 좋다.

### 3. keyword 생성 방식 점검

input_text only보다 keyword 포함 성능이 훨씬 좋았다.

따라서 실제 서비스에서도 keyword를 만들 수 있어야 한다. 다만 keyword가 정답 선택지 기반이면 누수 가능성이 있으므로, 문제 지문/질문/선택지만으로 keyword를 생성하는 방식이 필요하다.

### 4. 최종 추론 코드 작성

저장된 모델을 불러와 다음 흐름으로 예측하는 코드를 작성해야 한다.

```text
입력 문항
-> 전처리
-> keyword/core 생성
-> era 모델 예측
-> topic_train 모델 예측
-> 결과 저장
```
