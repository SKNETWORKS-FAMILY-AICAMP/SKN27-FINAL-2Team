# 선지 단위 문제 품질 검수 ML v15 최종 정리

## 1. v15 목적

v15는 생성된 한국사 5지선다 문제를 **선지 단위로 2차 검수**하기 위한 최종 운영 버전이다.

이 모델은 정답 번호를 맞히는 모델이 아니다.  
문항 안의 각 선지를 하나씩 보고, 해당 선지가 문제 품질상 이상한지 여부를 이진 분류한다.

```text
입력 X = 지문 + 질문 + 선지 1개 + 정답 여부
y = 이진 분류
label 0 = 오류 있음
label 1 = 오류 없음
```

모델 결과는 자동 폐기 기준이 아니라, 사람이 먼저 확인해야 할 **검수 후보**를 찾는 데 사용한다.

## 2. v15에서 사용한 모델

```text
model_name = klue/roberta-base
max_length = 512
epochs = 30
batch_size = 16
learning_rate = 2e-5
threshold = 0.1
```

`klue/roberta-base`를 사용한 이유는 한국어 문장 분류에 적합하고, 입력이 `지문 + 질문 + 선지`처럼 여러 문장 간 관계를 보는 구조이기 때문이다.

## 3. v15 입력 데이터

문항 1개는 모델 학습 시 선지 5개로 분리된다.

```text
문항 1개
→ 선지 1번 row
→ 선지 2번 row
→ 선지 3번 row
→ 선지 4번 row
→ 선지 5번 row
```

각 row에는 다음 정보가 들어간다.

| 입력 요소 | 설명 |
|---|---|
| 지문 | 문제의 자료 또는 설명 |
| 질문 | 문제에서 요구하는 조건 |
| 선지 1개 | 검수 대상 선지 |
| 정답 여부 | 해당 선지가 정답인지 오답인지 |

정답 여부를 넣는 이유는 모델이 정답을 맞히게 하려는 것이 아니다.  
같은 문장이라도 정답 선지인지 오답 선지인지에 따라 오류 기준이 달라질 수 있기 때문이다.

예를 들어 `정답 선지가 지문에 노출됨`, `정답 선지만 지나치게 짧음` 같은 오류는 정답 선지 여부를 알아야 판단하기 쉽다.

## 4. 사용 데이터

최종 학습은 v10 전처리 데이터를 사용하고, v15 노트북 내부에서 조합형/순서형 선지를 제외한다.

RunPod 기준 파일 구조:

```text
/workspace/
├─ train_choice_quality_runpod_v15.ipynb
└─ common/
   ├─ choice_quality_train_v10.json
   └─ choice_quality_test_v10.json
```

데이터 구성:

| 데이터 | 역할 |
|---|---|
| 기출 문제 선지 | 정상 선지 데이터 |
| 팀원 생성 사용불가 문제 선지 | 오류 후보 선지 데이터 |

주의할 점은 팀원이 준 문제가 문항 단위로 사용불가라고 해도, 선지 5개가 모두 오류라는 뜻은 아니라는 점이다.

예를 들어 문항 실패 이유가 `정답 선지가 지문에 노출됨`이라면, 실제 오류는 정답 선지 1개이고 나머지 오답 4개는 정상일 수 있다.

## 5. v15 주요 변경점

v15의 가장 큰 변경점은 **선지 하나만 보고 판단하기 어려운 유형을 ML 검수 대상에서 제외**한 것이다.

제외 대상:

```text
ㄱ, ㄴ
ㄱ, ㄷ
ㄱ, ㄴ, ㄷ

(가) - (나) - (다)
(나) - (다) - (가)
```

이런 선지는 선지 하나만 보면 의미가 부족하다.  
문항 전체의 보기, 자료, 순서 조건을 함께 봐야 판단할 수 있기 때문에 선지 단위 모델에 넣으면 오탐이 늘어날 수 있다.

따라서 v15에서는 이 유형을 다음처럼 별도 처리한다.

```text
검수상태 = 검수제외
참고코드 = EXCLUDED_COMBO_OR_ORDER_CHOICE
```

이 처리는 정상 판정이 아니라, **선지 단위 ML로 판단하지 않는 것이 맞다**는 의미이다.

## 6. threshold 기준

v15에서는 threshold를 `0.1`로 고정하였다.

```text
error_prob >= 0.1
→ 오류 후보

error_prob < 0.1
→ 통과
```

threshold를 낮게 잡은 이유는 이 모델이 자동 폐기 모델이 아니라 2차 검수 후보 추출 모델이기 때문이다.

오탐이 조금 늘어나더라도 실제 오류를 놓치지 않는 것이 더 중요하다.

## 7. v15 평가 데이터

v15에서는 조합형/순서형 선지를 제외한 뒤 평가하였다.

```text
학습 train: 6,600개
학습 validation: 1,655개
테스트 선지: 1,900개
학습에서 제외된 선지: 470개
테스트에서 제외된 선지: 165개
```

테스트 데이터 구성:

```text
정상 선지: 1,796개
오류 선지: 104개
```

데이터 출처별 테스트 구성:

| 출처 | 선지 수 | 실제 오류 | 실제 정상 |
|---|---:|---:|---:|
| 팀원 생성 문제 | 465 | 104 | 361 |
| 기출 문제 | 1,435 | 0 | 1,435 |

## 8. v15 모델 단독 성능

모델 단독 기준 성능:

```text
Accuracy: 98.37%
오류 Precision: 84.76%
오류 Recall: 85.58%
오류 F1: 85.17%
```

혼동 행렬:

| 구분 | 예측 오류 | 예측 정상 |
|---|---:|---:|
| 실제 오류 | 89 | 15 |
| 실제 정상 | 16 | 1,780 |

해석:

```text
실제 오류 104개 중 89개 탐지
실제 오류 15개 미탐
정상 선지 1,796개 중 16개 오탐
정상 선지 1,780개 정상 통과
```

## 9. v15 최종 성능

운영에서는 모델 예측만 사용하지 않고, 규칙 기반 검사 결과를 함께 사용한다.

최종 판정 기준:

```text
모델이 오류라고 판단
또는
규칙 기반 검사에서 오류 코드 탐지
→ 검수필요
```

모델 + 규칙 최종 성능:

```text
Accuracy: 98.53%
오류 Precision: 82.76%
오류 Recall: 92.31%
오류 F1: 87.27%
```

혼동 행렬:

| 구분 | 예측 오류 | 예측 정상 |
|---|---:|---:|
| 실제 오류 | 96 | 8 |
| 실제 정상 | 20 | 1,776 |

해석:

```text
실제 오류 104개 중 96개 탐지
실제 오류 8개 미탐
정상 선지 1,796개 중 20개 오탐
정상 선지 1,776개 정상 통과
```

모델 단독보다 최종 성능에서 오류 recall이 높아진 이유는, 모델이 놓친 일부 오류를 규칙 기반 검사에서 추가로 잡았기 때문이다.

## 10. v14와 v15 비교

v14 모델 단독 성능:

```text
Accuracy: 98.84%
오류 Precision: 89.08%
오류 Recall: 90.60%
오류 F1: 89.83%
```

v15 모델 단독 성능:

```text
Accuracy: 98.37%
오류 Precision: 84.76%
오류 Recall: 85.58%
오류 F1: 85.17%
```

v15는 v14보다 모델 단독 수치가 낮다.

하지만 v15는 성능 점수만 높이기 위한 버전이 아니라, 실제 운영 기준에 맞게 평가 대상을 정리한 버전이다.

v15에서 제외한 165개 선지는 선지 하나만 보고 오류 여부를 판단하기 어려운 유형이다. 이 유형을 계속 평가에 넣으면 숫자는 좋아 보일 수 있지만, 실제 사용에서는 불필요한 오탐과 해석 혼란이 생길 수 있다.

따라서 최종 운영 버전은 v15로 결정하였다.

## 12. v15 오류 코드 요약

최종 테스트 결과 기준 오류 코드 분포:

| 오류 코드 | 개수 | 의미 |
|---|---:|---|
| `ANSWER_LENGTH_BIAS` | 45 | 정답 선지가 다른 선지보다 유독 길거나 짧음 |
| `ANSWER_RESTATEMENT_SUSPECT` | 41 | 정답 선지가 지문 내용을 거의 재진술함 |
| `CHOICE_FORMAT_ERROR` | 22 | 선지 문장 또는 형식 오류 |
| `QUESTION_CHOICE_MISMATCH` | 6 | 질문 요구와 선지 형식이 맞지 않아 보임 |
| `ODD_DISTRACTOR` | 5 | 오답 선지가 너무 이상하거나 쉽게 제거됨 |
| `ANSWER_IN_PASSAGE` | 4 | 정답 선지가 지문 또는 질문에 노출됨 |

`QUESTION_CHOICE_MISMATCH`는 오탐 가능성이 있어 자동 오류가 아니라 참고 코드로만 사용한다.

## 13. 실제 사용 방법

팀원은 생성한 문제를 JSON으로 저장한 뒤, 공유 패키지의 추론 코드를 실행한다.

```bash
python predict_choice_quality.py \
  --model_dir ./model \
  --input ./generated_questions.json \
  --output_csv ./review.csv \
  --output_json ./review.json
```

결과는 `review.csv`에서 확인한다.

우선 확인할 컬럼:

| 컬럼 | 설명 |
|---|---|
| `검수상태` | 검수필요, 참고검수, 통과, 검수제외 |
| `오류확률` | 모델이 계산한 오류 가능성 |
| `판단근거` | model, rule, model+rule, advisory, none |
| `오류코드` | 오류로 판단한 이유 |
| `참고코드` | 참고용 오류 코드 |
| `지문` | 문제 지문 |
| `질문` | 문제 질문 |
| `선지` | 검수 대상 선지 |

## 14. 한계점

v15는 2차 검수 모델로 사용할 수 있지만, 다음 한계가 있다.

- 역사적 사실 자체의 참/거짓은 안정적으로 검증하기 어렵다.
- 문항 전체 논리나 복잡한 사료 해석은 별도 검수가 필요하다.
- 오류 코드별 데이터 수가 적은 항목은 설명 정확도가 제한될 수 있다.
- `ㄱ, ㄴ` 조합형과 순서형 선지는 선지 단위 판단에서 제외했기 때문에 문항 단위 검수가 필요하다.
- 모델 결과는 최종 판정이 아니라 검수 후보이다.

## 15. 최종 판단

v15는 현재 작업의 최종 운영 버전으로 사용해도 된다.

다만 사용 방식은 다음과 같이 제한해야 한다.

```text
자동 폐기 X
자동 정답 검증 X
검수 후보 추출 O
검수 우선순위 제공 O
최종 판단은 사람 O
```

즉 v15는 문제 생성 결과물을 바로 배포하기 전에, 검수자가 우선 확인해야 할 선지를 줄여주는 **2차 안전 검수 모델**로 사용하는 것이 가장 적절하다.
