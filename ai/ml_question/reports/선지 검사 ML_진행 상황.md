# 선지 오류 2차 검수 모델 진행 상황 및 사용 방향

## 1. 모델 목적

현재 만들고 있는 모델은 문제의 정답을 맞히는 모델이 아니다.

목적은 **문제 생성 후 각 선지에 오류가 있는지 없는지 2차 검수하는 것**이다.

문항 전체를 한 번에 평가하는 것이 아니라, 선지 1개씩 나누어 평가한다.

```text
결과 0 = 오류 있음
결과 1 = 오류 없음
```

## 2. 학습 입력 데이터

모델이 보는 input은 다음 4가지다.

```text
지문
질문
선지 1개
해당 선지가 정답인지 여부
```

예시:

```text
[지문]
문제의 자료 또는 설명

[질문]
다음 자료에 대한 설명으로 옳은 것은?

[선지]
간송미술관 소장본이 대표적이다.

[정답 여부]
정답 선지
```

정답 여부는 모델이 맞히는 값이 아니라, 입력 feature다.

예를 들어 다음과 같은 오류를 판단하기 위해 넣는다.

```text
정답 선지가 지문에 그대로 노출되어 있는지
정답 선지만 다른 선지에 비해 유독 짧거나 긴지
```

## 3. y값

학습 y값은 이진 라벨이다.

```text
label=0: 오류 있음
label=1: 오류 없음
```

모델은 선지를 보고 오류일 확률을 계산하고, threshold 기준으로 0/1을 결정한다.

```text
error_prob >= threshold → 0, 오류 있음
error_prob < threshold → 1, 오류 없음
```

## 4. 사용 데이터

현재 사용하는 데이터는 두 종류다.

```text
기출문제 선지
- 이미 검증된 문항
- 오류가 없는 정상 선지로 사용
- label=1

팀원 생성 문제 중 오류가 확인된 선지
- API 전수검사/분류 결과로 오류가 확인된 데이터
- 오류 선지로 사용
- label=0
```

문항 1개는 선지 5개로 나뉘기 때문에, 전처리 후에는 선지 단위 row가 된다.

```text
문항 1개 → 선지 row 5개
```

## 5. 오류 코드

오류 코드는 모델 결과를 사람이 이해하기 위한 보조 정보다.

주요 오류 코드는 다음과 같다.

```text
ANSWER_IN_PASSAGE
정답 선지가 지문/질문에 노출됨

ANSWER_LENGTH_BIAS
정답 선지가 다른 선지에 비해 유독 길거나 짧음

CHOICE_FORMAT_ERROR
선지 문장 또는 형식이 이상함

QUESTION_MARKER_MISMATCH
지문에 없는 밑줄, 표식, (가), (나) 등을 선지에서 참조함

WEIRD_CHOICE
문제 맥락상 너무 이상하거나 부적절한 선지

DUPLICATE_OR_SIMILAR_CHOICE
중복되거나 거의 같은 선지가 있음

NO_OR_MULTI_ANSWER
정답이 없거나 2개 이상임
```

모든 오류 코드를 BERT가 직접 학습하는 것은 아니다.

중복 선지, 정답 0개/2개 이상처럼 선지 5개를 같이 봐야 하는 오류는 규칙 검사로 보조 처리한다.

## 6. 학습 방식

학습 흐름은 다음과 같다.

```text
1. 원본 문제 데이터를 선지 1개 단위로 전처리
2. 지문 + 질문 + 선지 + 정답 여부를 input text로 생성
3. label=0/1 이진 분류로 BERT 계열 모델 학습
4. train 내부에서 validation 분리
5. validation 결과로 threshold 선택
6. test 데이터로 최종 평가
7. 학습된 모델과 결과 CSV 저장
```

현재 모델은 BERT 계열인 `klue/roberta-base`를 사용한다.

## 7. threshold 의미

모델은 선지마다 `error_prob`를 낸다.

```text
error_prob = 이 선지가 오류일 확률
```

threshold는 이 확률을 보고 오류/정상을 나누는 기준이다.

```text
error_prob >= threshold → 오류 있음
error_prob < threshold → 오류 없음
```

threshold는 사람이 임의로 정하는 것이 아니라, validation 데이터 성능을 보고 자동으로 선택한다.

v8/v9 실험에서는 대략 다음 기준이 나왔다.

```text
best_threshold = 0.2
```

즉, `error_prob`가 0.2 이상이면 모델은 오류 선지로 판단한다.

## 8. 학습 완료 후 팀원이 사용하는 방법

학습이 끝나면 팀원은 모델을 재학습하는 것이 아니라, 생성한 문제를 검수 모델에 넣어 결과를 확인하면 된다.

사용 흐름은 다음과 같다.

```text
1. 팀원이 문제를 생성한다.
2. 생성 문제를 선지 단위로 전처리한다.
3. 학습된 모델이 각 선지의 오류 확률을 계산한다.
4. threshold 기준으로 오류 있음/없음을 판단한다.
5. 규칙 검사 결과도 함께 반영한다.
6. 결과 CSV에서 검수필요 항목을 확인한다.
7. 오류가 맞으면 선지를 수정하거나 문항을 다시 생성한다.
```

## 9. 팀원이 확인할 결과 파일

팀원이 주로 볼 파일은 상세 분석용 CSV가 아니라 간단 검수용 CSV다.

```text
test_review.csv
또는 운영 시 생성되는 review.csv
```

주요 컬럼은 다음과 같다.

```text
검수상태
검수필요 / 참고검수 / 통과

우선순위
HIGH / MEDIUM / LOW

오류확률
모델이 이 선지를 오류라고 본 확률

판단근거
model / rule / model+rule / none

오류코드
어떤 오류로 의심되는지

지문
질문
선지
```

## 10. 검수상태 해석

```text
검수필요
모델이 오류 선지라고 판단한 항목이다.
우선 확인해야 한다.

참고검수
규칙 검사에만 걸린 항목이다.
오탐 가능성이 있으므로 참고용으로 확인한다.

통과
현재 2차 검수 기준에서 이상 가능성이 낮은 항목이다.
```

## 11. 우선 확인할 항목

팀원이 가장 먼저 확인할 것은 다음이다.

```text
검수상태 = 검수필요
```

그다음 오류확률이 높은 것부터 보면 된다.

```text
오류확률이 높을수록 모델이 더 확신한 항목
```

다만 오류확률이 높다고 무조건 폐기하는 것은 아니고, 사람이 최종 확인한다.

## 12. 현재까지의 방향

현재 모델은 완성된 자동 폐기기가 아니라 **2차 검수 보조 모델**이다.

즉:

```text
모델이 오류 후보를 먼저 골라줌
사람이 오류 코드와 지문/질문/선지를 보고 최종 판단
오탐/미탐 사례를 다시 모아 다음 학습 데이터로 보강
```

이 방식으로 운영하면 팀원이 모든 선지를 처음부터 다 확인하는 부담을 줄이고, 문제가 될 가능성이 높은 선지를 먼저 확인할 수 있다.

## 13. 현재 한계

현재 모델이 모든 오류를 완벽히 잡는 것은 아니다.

특히 다음은 한계가 있다.

```text
역사적 사실 자체가 맞는지 검증하는 것
문맥상 미묘하게 어색한 선지
데이터가 적은 오류 유형
규칙 검사에서 생기는 오탐
```

따라서 이 모델은 최종 검수자를 대체하는 것이 아니라, 2차 검수에서 우선 확인할 선지를 추천하는 모델로 사용하는 것이 적절하다.
