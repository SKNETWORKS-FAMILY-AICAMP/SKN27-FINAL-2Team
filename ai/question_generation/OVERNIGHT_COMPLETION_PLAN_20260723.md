# 문제 생성 파이프라인 야간 완성 계획

- 작성일: 2026-07-23
- 범위: `ai/question_generation/`과 현재 300문항 실행 산출물
- 목표: 평가 비용을 낮춘 뒤 중단된 300문항을 이어서 수리하고, source-level 후처리와 최종 신규 5문항 검증까지 완료한다.
- 원칙: 처음부터 재생성하지 않음, topic별 하드코딩 금지, 문자열 치환 휴리스틱 금지, Gate 완화 금지, 기존 checkpoint 우선 사용
- 비용 상한: 이 계획 실행 이후 발생하는 OpenAI API 비용은 총 `$20` 미만. `$17`부터 신규 작업을 중단하고 남은 `$3`는 이미 시작한 요청의 재시도·마무리 여유로만 사용한다.

## 0. 사용자가 확인할 최종 결과

아침 최종 보고는 다음 네 항목으로 시작한다.

```text
300문항 완료
평가 최적화 완료
후처리 코드 완료
신규 5문항 테스트 이상 없음
```

각 항목의 의미:

- `300문항 완료`: 최종 300문항이 저장되고 평가·수리 상태와 문항별 이력이 확정됨
- `평가 최적화 완료`: 30문항 비교 실험, 방식 확정, 코드 반영, 실측 비용 비교가 끝남
- `후처리 코드 완료`: source-level 결함을 기존 evidence 우선, owner-scoped RAG 차선으로 복구하는 재사용 가능한 경로가 구현·검증됨
- `신규 5문항 테스트 이상 없음`: 모든 변경 이후 새 실행 폴더에서 5문항을 처음부터 생산하고 최종 평가까지 통과함

하나라도 충족하지 못하면 네 줄을 완료로 표시하지 않는다. 완료된 항목, 미완료 항목, 정확한 중단 원인과 재개 지점을 구분하여 보고한다.

## 2. 완료 조건

다음 조건을 모두 충족해야 완료로 본다.

1. 30문항 고정 표본으로 평가 후보들을 비교하고 비용 대비 정확도가 가장 좋은 방식을 확정한다.
2. 확정한 평가 방식만 최소 수정으로 반영한다.
3. `ai/question_generation/` 전체를 현재 코드 기준으로 다시 검사한다.
4. 기존 300문항을 처음부터 재생성하지 않고 checkpoint에서 이어서 처리한다.
5. 116문항은 평가가 지목한 컴포넌트만 수리한다.
6. source-level 결함 12문항은 evidence 재선택 또는 owner-scoped RAG로 복구한다.
7. 최종 300문항에 미완료, 중복 ID, 평가 자기모순, 잘못된 정답이 없어야 한다.
8. 모든 변경이 끝난 최종 코드로 신규 5문항을 처음부터 생산하고 전체 파이프라인 동작을 확인한다.

## 3. 단계별 실행 계획

### 단계 A. 작업 목록 동결

현재 `cycle_0.jsonl`, 문항 checkpoint, pack 원본을 읽어 300문항의 처리 목록을 한 번만 만든다.

각 문항은 정확히 하나에만 속해야 한다.

```text
keep
component_repair
source_repair
```

동일 문항을 일반 재생성과 source 후처리에 중복으로 넣지 않는다. 생성 전후의 문항 해시와 기존 `repair_history`를 보존한다.

### 단계 B. 30문항 평가 비용 실험

문항 생성은 하지 않고 동일한 완성 문항 30개만 평가한다.

표본 구성:

- 정상 PASS 문항
- 선지 문장 파손
- 선지 역사 사실 변형
- 복수정답·정답 없음
- 지문 역사 사실 오류
- 정답 누출
- 고난도 정상 문항
- 평가기 오판 문항
- basis/evidence 후처리 문항
- `needs_verification` 문항

비교 후보:

1. 현재 평가 프롬프트와 현재 모델
2. 축약 프롬프트와 현재 모델
3. 저가 모델과 강한 모델의 역할 분리
4. 저가 모델 평가 후 애매한 결과만 강한 모델이 재판정

모든 후보에 같은 30문항과 같은 정답 기준을 사용한다. 생성 결과를 고치거나 후보별로 입력을 다르게 만들지 않는다.

측정 항목:

- Gate 결과 일치
- 역사 오류·복수정답의 거짓 PASS 수
- `repair_targets` 일치
- `target_feedback`의 수리 가능성
- 입력 토큰, 캐시 토큰, 출력 토큰
- 문항당 비용
- 문항당 시간

선택 규칙:

1. 역사 오류 또는 복수정답을 정상으로 통과시키는 후보는 제외한다.
2. 수리 대상 컴포넌트를 잘못 지정하는 후보는 제외한다.
3. 남은 후보 중 문항당 실측 비용이 가장 낮은 방식을 선택한다.
4. 비용 차이가 미미하면 호출 수와 상태 전이가 단순한 방식을 선택한다.

### 단계 C. 평가 개편 최소 반영

단계 B에서 이긴 방식만 반영한다.

허용 변경:

- 평가 프롬프트에서 중복 설명 제거
- 평가 역할에 맞는 모델 교체
- 기존 명시적 캐시 유지
- 모델별 입력·출력 사용량 기록

금지 변경:

- Gate 기준 완화
- topic·인물·사건별 예외
- 문자열 포함 여부로 역사 사실을 판단하는 임시 규칙
- 평가 결과를 억지로 PASS시키는 정규화
- 사용하지 않을 확장 구조와 추상화 추가

### 단계 D. 변경 후 코드 전수검사

범위는 전체 프로젝트가 아니라 `ai/question_generation/` 현행 경로로 제한한다.

필수 검사:

- 평가 응답 strict validation
- `PASS`, `FAIL`, `uncertain`, `needs_verification` 상태 전이
- `repair_targets`와 `target_feedback` 전달
- 정답과 오답별 피드백 분리
- SLLM 재시도 2회와 GPT fallback
- 해당 컴포넌트만 초기화·재생성하는지 여부
- checkpoint 원자적 저장과 resume
- 동일 문항·동일 해시 평가 중복 호출 방지
- pack 입력 계약과 evidence owner 일치
- V41 허용 필드와 실제 필드값
- 활성 코드의 legacy·graph_path 의존성
- 하드코딩, 임시 휴리스틱, 불필요한 중복 계층

검증 명령은 프로젝트 가상환경을 사용한다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s ai\question_generation\tests -p "test_*.py"
.\.venv\Scripts\python.exe -m compileall ai\question_generation
git diff --check
```

### 단계 E. 기존 300문항 수리 재개

새 output 폴더에서 300문항을 다시 생성하지 않는다. 현재 실행 폴더와 checkpoint를 사용해 `--resume` 경로로 이어서 처리한다.

처리 원칙:

```text
keep              기존 문항과 평가 결과 유지
component_repair  지목된 material/question/correct/distractor:N만 재생성
source_repair     일반 재생성에서 제외하고 단계 F로 전달
```

일반 수리는 다음 순서를 유지한다.

```text
SLLM 피드백 기반 부분 재생성 최대 2회
→ 실패한 동일 컴포넌트만 GPT 수리
→ 수정된 완성 문항만 재평가
```

완료된 지문·정답·오답과 정상 161문항은 다시 호출하지 않는다. 고난도 정상 9문항은 난이도만 재분류하고 문장을 재생성하지 않는다. 평가기 오판 2문항은 기존 문항을 복구한다.

### 단계 F. source-level 후처리

대상은 12문항으로 제한한다.

#### F-1. owner 전용 basis가 필요한 문항

```text
5    양양 오산리 선사유적
12   삼한
31   신라
32   백제
74   무령왕
77   내물마립간
97   별무반
224  형평운동
253  사찰령
```

31번과 32번은 같은 발해 불교 basis 하나를 공유하므로 실제 교체 basis는 8개이다.

처리 순서:

```text
현재 evidence chunks에서 직접적이고 owner 전용인 사실 재선택
→ 없으면 같은 owner 범위에서 키워드 RAG
→ 부족할 때만 vector/reranker RAG
→ basis와 evidence_chunk_ids 함께 갱신
→ 해당 컴포넌트만 재생성
→ 완성 문항 재평가
```

직접 근거가 없으면 기존 basis를 재사용하거나 추정하지 않는다.

#### F-2. material-answer 연결을 맞출 문항

```text
99   전시과: 경정전시과 자료와 시정전시과 정답
256  조선교육령: 제3차 자료와 제1차 정답
300  경제개발계획: 제2차 자료와 제1차 정답
```

먼저 기존 evidence 안에서 같은 세부 대상끼리 연결한다. 적합한 짝이 없을 때만 owner-scoped RAG를 호출한다.

#### F-3. 후처리 도구 범위

새로운 파이프라인을 만들지 않는다. 기존 문항 checkpoint와 평가 결과를 읽고 기존 생성 함수를 호출하는 얇은 복구 진입점만 둔다.

필수 입력:

- 문항 checkpoint
- 실패 이유
- 수리 대상
- 기존 SLLM 요청·응답
- basis item과 owner
- evidence chunk IDs

필수 출력:

- 변경된 basis 또는 연결 정보
- 호출한 컴포넌트
- 이전·이후 문항 해시
- 재평가 결과
- 누적 수리 이력

문항을 폐기하는 `deferred` 경로는 만들지 않는다. 직접 근거가 없어 완료하지 못한 문항은 원인과 함께 복구 큐에 남긴다.

### 단계 G. 300문항 최종 확정

최종 검증:

- 문항 수 300
- 문항 ID와 variant key 중복 없음
- 모든 문항 checkpoint 완료
- 최종 Gate 상태 확정
- 표시 정답과 정답 유일성 확인
- 지문 사실성 및 정답 누출 확인
- 선지 5개와 source metadata 보존
- 난이도·시대·지문 유형 분포 집계
- 일반 수리와 source 수리 이력 보존
- 총 생성·평가·재생성 호출과 실측 비용 보고

### 단계 H. 최종 시스템 신규 5문항 생산

모든 코드 변경과 300문항 복구가 끝난 뒤, 기존 checkpoint를 사용하지 않는 새 실행 폴더에서 신규 5문항을 처음부터 생산한다.

확인 범위:

- pack 선택과 owner 회전
- 지문 유형 비율 적용
- 110~180자 지문 권장 범위
- 정답·오답 V41 입력
- 평가 모델 라우팅과 캐시
- 평가 피드백 기반 부분 재생성
- SLLM 재시도와 GPT fallback
- 최종 문항 조립과 저장
- 비용·시간·repair history 기록

최종 5문항은 사람이 읽을 수 있는 Markdown과 원본 JSON을 함께 남긴다.

## 4. 야간 작업 중 중단 조건

다음 상황에서는 비용을 계속 쓰지 않고 중단하고 기록한다.

- 30문항 실험에서 저가 평가기가 역사 오류 또는 복수정답을 PASS시킴
- 동일 컴포넌트가 정해진 재시도 이후에도 같은 오류를 반복함
- checkpoint 해시와 평가 대상 문항이 일치하지 않음
- source repair에서 owner 직접 근거를 찾지 못함
- API·RunPod·DB 장애로 요청 결과의 완전성을 보장할 수 없음
- 예상하지 못한 대규모 스키마 변경이 필요함

중단은 문항 폐기를 뜻하지 않는다. 완료된 상태를 저장하고 남은 문항과 원인을 복구 큐에 기록한다.

## 6. 예상 운영 시간

기존 300문항 생성 결과와 checkpoint를 재사용하므로 처음부터 300문항을 생성하는 작업보다 짧다. API·RunPod·DB가 정상이고 source 근거가 현재 evidence에서 대부분 발견된다는 조건에서는 야간 한 번의 연속 작업으로 완료 가능한 범위다. 외부 서비스 지연이나 직접 근거 부재가 발생하면 완료된 checkpoint를 보존하고 해당 문항만 남긴다.
